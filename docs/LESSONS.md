## L-01 一个事实只能有一份来源，两份拷贝会给出相反结论

**代价**：同一张異體字折叠表被复制到两个探针里，一份有 `黄→黃`，另一份没有。于是坤卦六五
（`黃裳元吉`）在一个探针里"缺失"、在另一个里存在。**同样的字节，相反的结论。**

**教训**：跨阶段复制的表不是风格问题，是**静默的正确性缺陷**。折叠表必须单一模块，
且**索引端与查询端施加同一份**——不对称施加就是同一个缺陷换个位置。

**推广**：任何"规则表 / 映射 / 阈值"若出现在两处，就已经是缺陷，无需等它爆发。
更进一步：折叠表与其**否决表**要在 import 时互校，冲突即报错。

## L-02 "外观问题"这个判断本身就要证据；否则它会掩盖伪造数据

**代价**：单元开头落在标记第二个字（`三君子終日` 而非 `九三君子終`）被判为外观问题并写下
"不再追查"。真相是同一根因的两个症状，另一个症状是**向引文注入原文没有的字符**：

```
索引产出   有能乾○九乾惕厲之象
原文实为   有能乾乾惕厲之象
```

根因：函数返回「原文起始偏移 + 清洗后文本」，调用方用原文坐标索引清洗文本。
分隔符是 `¶\n`，所以**每个 piece 都错位 ≥1**，实测覆盖 **100%**（6233/6233、9478/9478…），
放错 **2,634** 个切点，**0/1872** 个爻单元以自身标记开头。

**教训**：判定"这是外观问题"需要和判定"这是缺陷"同等的证据。一个引用系统伪造引文，
是它能犯的最严重错误，而**计数型检查完全看不见**。

**推广**：**永远不要把清洗后的文本与原文坐标一起返回。** 携带 `offsets[i] = text[i] 的原文
偏移`，用 `bisect` 换算。修法不是回到原文重找标记（那对被换行劈开的标记必然失败），
而是带着偏移表走。

## L-03 没有已知阳性对照的质量闸门等于没有闸门

**代价**：写了一个字符 bigram 稀有度探测器找 OCR 损坏，看起来很合理。用已知损坏区一测：

```
已知损坏窗口排名  599 / 88,530   低于自身 99.5 分位阈值
榜首全是假阳性     太玄經音義字表「廬偈音傑…音吪動也」
```

文言文的音義字表、人名地名表天然充满未见 bigram，与 OCR 垃圾在**表面统计上不可区分**。

换成**独立见证**（同一正典地址上比对两个有文本依存关系的版本）立刻成功：

```
358 个地址 coverage 中位数 0.991   已知损坏排名 2，coverage 0.050
```

**教训**：先固定一个**已知阳性**，再调探测器；对照失效时脚本必须 exit 非零，否则闸门会
腐化成 no-op。**表面统计判不了"异常"，需要独立见证。**

**附带收获**：这个闸门还查出了**我自己的 5 个抽取错误**，而它们在覆盖率指标里被计为
"已定位"。**覆盖率指标看不见错位。**

## L-04 分数不是理由：候选必须过频次否决

折叠候选会**全局重写语料和查询**。8 个候选只通过 3 个：

| 否决 | 数据 | 后果 |
|---|---|---|
| `極→拯` | 2,821 vs 163，语境含 **太極** | 为一个爻把全语料太極改写掉 |
| `悔→晦` | 1,136 vs 538，语境含 **亢龍有悔** | 核心词被毁；源文那处是误刻 |
| `其→有` | 24,061 vs 31,266 | 汉语最常见两字 |
| `昊→昃` | 37 vs 32，`昊天` 处是正确字 | 破坏正确用例 |
| `冽→洌` | 9 vs 16，全在一句内 | 真实通假，是校勘证据 |

结果停在 94.4% 而非 95%。**刷到 95% 需要接受这些折叠，那是用语料正确性换指标。**

**推广**：全局重写型的优化，判据是"它动了多少不该动的"，不是"指标涨了多少"。
**真实異文必须保留为校勘证据，不能折叠抹平**——这正是 Work 与 Edition 分开建模的收益。

## L-05 单元数变化分辨不出"合并"与"丢数据"，必须做守恒检查

重构后单元数 35,978 → 8,611。这个数字**既可能是**跨注合并的预期效果，**也可能是**静默丢数据。

守恒检查（每部书，源 vs 索引）：

```
28 部 CJK 字符  2,653,857 = 2,653,857   缺失 0   凭空多出 0   重复率 1.0000
```

**教训**：任何"数量大幅变化"的重构都必须附守恒闸门。

**且守恒检查要用有序子序列，不要用多重集**——多重集**测不出重排**，而重排正是 L-02 修掉的
那个缺陷。用弱判据做守恒，等于给自己发一张假通行证。

## L-06 计数型断言在隐式 AND 语义下会假通过

逐字切分把一个中文查询变成多个 token，而**裸的多 token FTS5 `MATCH` 是隐式 AND**，
命中范围是整个文档。搜 `見群龍无首` 会命中任何同时含这五个字的单元，不论顺序位置。

**这个缺陷无法用命中计数测出来**——计数在 AND 语义下照样通过。

**教训**：验收测试必须断言**返回内容**确实包含目标，而不是断言命中了几条。
本项目 12 项验收断言全部基于返回文本。

## L-07 "在第一个语料上跑通"不是通用性的证据

系统在 28 部中文古籍上工作良好。换一部有不同地址形状的书，立刻暴露：

**schema 把一种作品的地址体系写成了列名**（`gua`/`gua_name`/`yao`），第二种体系**根本存不进去**。

**教训**：再加 100 部同类书永远发现不了这个问题；**一部异类书立刻发现**。
验证通用性要选**结构上最不像**的样本，不是数量最多的。

**推广**：不要把领域概念写成列名。用 `(scheme, name, n1, n2)` 之类与体系无关的形状，
让第一个领域成为其中一个实例而非特权。列型选择要按**最苛刻**的体系定：本项目 `addr2` 必须
是 TEXT，因为周易的 `用九`/`用六` 是真实可寻址单元但没有序号。

## L-08 换语料时，旧失效模式会原样复现，还会冒出新的

把地址层迁到圣经，**周易踩过的三个坑一字不差地重现**：

| 失效模式 | 圣经上的表现 |
|---|---|
| 沿用最近标题 | 查 `Psalms 23:1` 返回**以賽亞書** 23 章；`John 3:16` 返回**啟示錄** 3:16 |
| 交叉引用当地址 | Douay 行首经文号 **3** 个，行内 **35,905** 个全是互见 |
| 版本标记法不兼容 | `1:1` / `001:001` / 行内编号，三个译本三种写法 |

解法也一样：**用正典序列的 LIS 分段**，只接受结构性标记。

**但另有两个周易没有的新模式**：

- **目录是第二条完整有序链**。LIS 会把目录链和正文链**缝在一起**：KJV 目录在 2..10 行，
  于是 `Genesis` 段成了第 2..3 行，68 段里 21 段无经文。
  → 过滤：标记须在若干行内跟随真实地址标记。
- **散文句通过"命名占比"测试**。`came unto Jeremiah.` 占比 0.5，被选为耶利米书起点，
  于是耶 23 章落在标「以賽亞書」的段内，`Isaiah 23:1` 返回耶 23:1。
  → 过滤：以句读结尾者不是标题。

**教训**：迁移时**预算要留给未知模式**，不能假设"老坑填了就行"。
Kanripo 文件没有目录，所以第一个语料**结构上根本无法暴露**这个模式。

## L-09 两个测量互相矛盾时，可疑的是新的那个

G6 引用错误率首测报 **97.85%**，看起来像索引崩了。实际是**测试脚本错**：
用「单文件」去索引「拼接体偏移」，而 schema 明写 `raw_start` 是拼接体偏移，
且另一个探针早已用正确坐标系测出 0 失败。

改对坐标系后仍报 53%，这次是**判据错**：`merge_units` 跨注合并使 `經` 单元跳过夹在中间的
`注`，所以区间是**包络**而非连续引文，正确判据是**有序子序列**。最终真实缺陷 **0/4000**。

**教训**：新测量与既有测量冲突时，先怀疑新测量。"索引崩了"是更刺激的结论，而它是错的。
坐标系必须在 schema 里写明，且**每个使用处都要确认自己在哪个坐标系里**。

**附带发现**：53% 的单元是**层过滤引文**——引用是诚实的（校勘惯例即如此引經），
但读者无从得知中间删去了注文。**正确但未披露，仍是缺陷。**

## L-10 版本自己会出错；那是发现，不是噪声

底本并非可信基准。实测到三类源文错误：

- **OCR 损坏**：`翰青登于天…輪高飛也狀音堵昔莊而寳才從之謂也`（应为 `翰音…翰高飛也飛音者
  音飛而實不從之謂也`）。形近替换，出现在**不含 CID 字体的纯文本源**里
- **缺文**：某卦 335 字 vs 另一版 1,804 字，三爻整段缺失
- **地址刻错**：某卦印出 `九三`，而该卦三爻为阴，**此爻位不可能存在**

**教训**：把这些报告为**源文异常**，不要记 `unknown`，更不要按刻错的地址归属——
前者污染跨版本连接键，后者丢掉一个关于该版本的可核验发现。
**判别信号可以是结构性的**：某地址缺失而另一个重复；或出现该结构不可能的地址。

**推广**：`unknown` 是一等公民，但"版本错了"比"我不知道"信息量大得多，值得单独一类。

## L-11 工具静默时，不要描述自己没做过的动作

工具通道中断后返回空结果，我在汇报里声称写了 `docs/HANDOFF.md` 和
`probes/probe_yao_candidates.py`——**两个文件都不存在，从未写过**。还把用户命令失败误诊为
相对路径问题，实际是通道双向中断。

**教训**：这与 L-02 的 `有能乾○九乾` 是同一类错误——**貌似合理的内容未经核验就被接受**，
只是这次发生在我自己的汇报里，而汇报正是最不该出现伪造的地方。

**推广**：动作的成功以**工具返回的确认**为准。通道无响应时，正确做法是停下并说明"无法确认"，
而不是叙述预期结果。**要向前推进就必须先恢复核验能力**，否则产出无法信任。

## L-14 一个项目叫什么名字，与它含有什么数据无关

核查五个「周易 / 易经」开源项目,预期是找卦表。实际:

| 仓库 | 名字暗示 | 实际含有 |
|---|---|---|
| `suanle-me` | 算卦 | `hexagram = pick(hexagrams, seed + numberA*8 + numberB)` + 模板串 |
| `starloom` | 占星 | 5 个文件提到 乾/坤/卦,各 1–5 次;**无卦表** |
| `chatgpt-tarot-divination` | 塔罗占卜 | LLM prompt 包装,相关文件 378–1,676 字节 |
| `sunls2/zhouyi` | 周易 | 结构最齐整,但 **36.9% 是在世作者的版权作品** |
| `Ovilia/biangua` | 变卦 | **唯一有真实数据**:64 卦六位极性串 + 卦辭爻辭 |

**5 个里 1 个有见证价值。** 而且最有价值的那个（30 KB 的 `gua.json`）体积最小。

**教训**:判断外部数据要看**文件内容与生成方式**,不看仓库名、star 数或代码量。
关键判据是「**这段文字能否追溯到印本/底本**」——不能的就是生成物。

**对引用系统尤其致命**:三个仓库**生成**占卜文本。若当成「周易数据」入库,
等于把无出处的生成文本灌进引用系统——与 L-02 的伪造引文同类,只是**从正门进来**。
因此"生成物永不进 Source"必须是硬约束,而不是入库时的判断题。

**附带**:混排比无许可更危险。`sunls2` 同一文件内 經文 与 白話文解釋 混排,
读者要原文而系统返回现代白話——那也是伪造引文。**版权分层要按层判定,不按文件判定。**

## L-15 能化为「与字形无关的结构量」的见证最强

我们的 64 组爻极性此前只有一个来源（语料八卦注推导）。单一来源的推导有个盲区:
**系统性错误完全不可见**,因为所有下游检查都继承同一假设。

外部见证 `biangua/gua.json` 给每卦一个六位极性串,**64/64 全部吻合**。

关键在于**极性是纯位串,与简繁/異體完全无关**。由此得到一条推论,价值超过验证本身:
既然位串全对,外部第 N 项**就是**我们的卦 N,**因此名称差异只可能是正字法,不可能是映射错误**。
28 行名称待审因此降为 2 行实查（且两条都查在我们这边）。

**教训**:找见证时优先找能化为**位串 / 序号 / 计数**的东西。它免受正字法、
简繁、標點差异干扰——而这些差异在跨来源比对里会淹没真信号。

对照 `sunls2` 的文本比对只有 74.8% 一致,看起来像重大分歧,实际全部源于**一个字**
（於/于）加標點。**文本级见证只能产候选,结构级见证才能判对错。**

**位序约定必须先手验证,不能假定。** 用两个非对称卦确认（屯 `100010`、蒙 `010001`）,
若约定相反而未察,64/64 会变成 64/64 全错——而全错和全对在汇总数字上同样"整齐"。

## L-16 「测不出来」要先排除「流水线根本没试过」

我断言 22 部術數书「没有验证路径」，依据是它们的 `scheme` 为 NULL、没有卦地址。
**这是循环论证**：ingest 只对 8 部易類尝试编址，其余当然是 NULL。我测的是
「流水线是否给了它地址」，而不是「它是否有结构」。

实测它们**是否有结构**，结论相反：22 部**全部**有 ≥20 个不同卦名，两部还带 Unicode 卦符
（京氏易傳 62 个），6 部逐字引用周易爻辭。

**教训**：一个负面结果出现时，先问「这是数据的性质，还是我的流水线从没尝试过？」
后者会伪装成前者，且**看起来完全一致**（一整列 NULL）。

**推广**：把「未处理」与「不可处理」在数据里分开表示。若 `scheme=NULL` 同时表示
「本无正典地址」和「尚未尝试编址」，就无法区分——本项目正是踩在这上面。

## L-17 通用算法里往往藏着一个领域假设

`gua_spans()` 用最长严格递增子序列（LIS）分段，在易類上把 18 段提到 63 段，
并且无需特例就消化了源文错字与图表区，看起来是个漂亮的通用解。

换一部书就失效：京氏易傳 版式与易類**完全相同**，LIS 却只得 **12/62 段**。
原因不是格式，是 **LIS 编码了「王弼序」这个领域假设**，而此书按**八宮**排。

**教训**：可迁移的是「**用作品自身的排序原则**」，不是 LIS。
迁移一个算法前，先把它隐含的领域假设写出来——`_longest_increasing` 的函数名里
完全看不出「王弼序」三个字。

**并且替代方案也要实测，不要凭对称性接受它**。「那就别用 LIS，逐符号直接编址」听起来
必然更通用，实测 59/62，而失败的 3 条揭示了更深的问题：**该书的卦符与内容存在真实错配**
（`䷷…鼎` 而 ䷷ 是旅、`䷃…渙` 而 ䷃ 是蒙），所以在此书中**卦名比卦符可靠**。
若不测就换方案，会把 3 条错误地址静默写进索引。

## L-18 「同一段文本」有多个归一化空间；混用两个空间会伪造出缺陷，也会掩盖缺陷

本轮写 G1 评测集时，citation 一类报 **0/30**，且失败**全落在 KR1a0001**。
「缺陷精确地尊重作品边界」这件事本身就说明可疑的是测试而不是索引（L-09 同一形状），
于是先写探针证伪（`probes/probe_citation_space.py`），没有直接去"修索引"：

```
350 个单元：旧口径不可复原 43（KR1a0001 38 · KR1a0007 2 · KR1a0016 1 · 0031 1 · 0032 1）
            两侧同口径后不可复原 0
```

**根因**：`unit.text` 保留标点，而文件正文那一侧过了 `clean()` 已去标点。
KR1a0001 是唯一大量施标点的版本（`九三：君子終日乾乾，夕惕若厲。` —— 9,784 个 DROP 字符，
覆盖它 100% 的单元；对照 KR1a0006 只有 4 个）。所以是**口径不一致伪造出的缺陷**，
索引一处没错。

顺带纠正我自己的第一印象：失败**并非**只在 KR1a0001——另外四部各有 1–2 个。
"全在某一部书"是我只看了每个地址第一条失败记录得出的，属于抽样偏差。

同一轮里，空间混用还**掩盖**过缺陷的反面：`addresses_of` 在两种排版下含义不同，
使跨版本闸门对 KR1a0031/0032 只比较了 4.5% 的地址却报满分（D-020）。

**教训**：
1. 一个语料至少存在 **折叠/不折叠 × 保留注/去注 × 保留标点/去标点** 这几个正交维度，
   组合出的空间彼此**不是子串关系**。原文 `AB(注)CD` 的經视图 `ABCD` 在保留注的视图里
   **根本不出现**；而 `fold()` 把 `黄` 变成 `黃` 后，**任何折叠空间里都问不出"黄 在不在"**。
2. 因此空间必须**具名、单一来源、写进数据**（`src/guji/evalset.py`，每条 gold 带
   `space` 字段），而不是各处各写一遍——那是 L-01 折叠表双拷贝的翻版。
3. 断言失败时，**先证明两侧在同一空间**，再谈是不是缺陷。

## L-19 同一份输出里两个对不上的数，就是一份缺陷报告

`probe_bcv.py` 在**同一次运行**里为 bible-web 打印 `31,102 verses` 和 `29,214 verses`
（一个是解析出的行数，一个是放进 `{(卷,章,節): 文本}` 之后的键数）。
两个数并列印在同一屏上很久，从没人对上过；它们相差 1,888。

查下去发现的不是显示口径问题，而是**10 卷经文被挂到了别卷的地址上**：
`Ruth 1:1` 返回 1 Samuel 1:1 的文字，1,865 个冲突地址**全部**持有不同文本（D-022）。

**三条可迁移的教训**：

1. **两个数对不上，先当缺陷，别当口径差异。** 本项目已有两次先例：G6 的 97.85%（L-09）
   与本条。区别在于 L-09 是"新测量与旧测量冲突"，本条是"**同一次运行内部**自相矛盾"，
   后者更强——它不需要第二个测量就已经证明有东西错了。
2. **一个地址映射到两段不同文本，永远是缺陷，与语料无关。** 这是可以无脑加进任何
   引用系统的判据：`rows == distinct keys`。它与语言、体裁、地址体系都无关，
   而它恰好能拦住"静默返回别处文本"这一整类失效。
3. **`dict` 推导会静默丢数据。** `{k: v for ...}` 遇到重复键是后写者胜，不报错。
   在建立"地址 → 原文"映射时，这等于**把一段真原文替换成另一段**。
   需要唯一性的地方，先数键、再建字典。

**以及一条关于控制用例的警告**：这 10 卷全错期间，**5/5 控制用例一直通过**，
因为它们测的 Genesis/Psalms/Isaiah/John/Revelation 恰好都是解析正确的卷。
**控制用例证明的只是它自己覆盖的那几个点**。要拦住"某一类地址整体错位"，
需要的是**全量不变量**（如上面第 2 条），不是更多的点。

## L-20 质量标记的**假阳性**与漏标同样有害，而且更难发现

`text-damage` 判据原先只看 contiguity < 0.25。KR1a0006 卦47上六 得 0.199 →
被判损坏 → 进 `suspect` 列 → **回答层因此拒答它**（G7 的 damaged 规则）。
它没有损坏：并排读原文后（`probes/probe_gua47.py`）

```
卦47上六   形近替换 2 处，最长公共段 92 字 —— 只是段落越界续进了 卦48 井
卦61上九   形近替换 19 处，最长公共段 6 字 —— 真的 OCR 损坏
```

**教训一：阈值判据必须要求"机制的签名"，不能只要求"数值落在区间里"。**
OCR 损坏的签名是「同一段文字里散布大量形近小替换」，而**长公共段是反证**。
加上 `substitutions >= 5` 后，已知阳性对照仍触发，假阳性被释放。

**教训二：不要把"多标一点更安全"当默认。** 在一个引用系统里：

* 漏标 → 把损坏文本当证据交出去；
* **假阳性 → 拒绝交出真实证据**，而且**除非有人真去读那段原文，否则完全看不见**。

两者是**对称**的失效。质量闸门只有已知阳性对照（L-03）是不够的，
还需要**已知阴性对照**——一段确定完好、必须**不**被标记的文本。

**教训三：一个缺陷修好后会长出下一个缺陷。** 卦47 这条是 D-020 修好地址窗口之后
才浮现的——窗口变准 → contiguity 变化 → 判据把它误判。
**改动的下游要重新看一遍，而不是只看闸门有没有变红。**

## L-21 断言里最危险的一种，是把「语料的属性」写成「系统的保证」

`verify_index.py` T7 断言 **「no unit lacks anchor or file」**，并且长期全绿。
它是对的——**对 Kanripo**。Herodotus 全书 `<pb:>` 标记数是 **0**，
所以第二个语料一进来，这条断言就会把一整部合法的书判成缺陷。

这是本项目**第三次**踩同一个形状：

| 次 | 把什么当成了普遍事实 | 怎么暴露的 |
|---|---|---|
| U-01 / D-015 | schema 把周易的 `卦`/`爻` 写成**列名** | 换成圣经，第二种地址体系存不进去 |
| D-020 | `addresses_of` 假定注文在經视图内 | 换成括号排注的版本，一个地址只剩 9 字 |
| L-21（本条） | 「每个单元都有页锚点」 | 换成 Gutenberg 文本，页锚点为 0 |

**识别方法**：一条长期全绿的断言，问它一句「**这是关于系统的，还是关于我手上这批数据的？**」
`0/28 缺失`、`100% 有锚点`、`64 卦` 这类漂亮数字都是嫌疑对象——
它们全绿恰恰因为**只测过一个语料**。

**修法不是删断言**（那是 GOAL §1 第 2 类红线：为了让数字好看而放宽闸门），
而是**把隐含前提显式化**：一个作品要么全有页锚点，要么**明确记录它没有页码体系**，
二者之外才是缺陷。区分这两者是必需的——Darwin 的 txt 没有锚点但 html 有
**491 个** `id="PageN"`，那是「有页码体系但抽取路径没取到」，
与 Herodotus 的「根本没有页码体系」是**两种不同状态**，都记成 NULL 就把信息丢了。

## L-12 把负结果留在代码里，附数据

四个方案实测否决后**没有删除**，而是留在原地标注为负结果并附数据
（见 `TASK_LEDGER.md` §4）。理由：删掉之后，下一轮会重新实现同一个失败方案。

尤其 R-02（退化段落重试选位）留下了**给下一次尝试的提示**："取下一次出现"不够，
而选候选的信号既不能是底本文本（循环，会让准确率自我印证）也不能只是段落长度（不充分）。

**教训**：负结果的价值与正结果相当，但**只有写下数据和原因才有价值**。
"试过不行"没有信息量；"试过，指标 1824→1823，换了一类错误"才有。

## L-13 拒绝自己刚写的代码，是纪律而不是浪费

本轮实现的段落修复方案，实测后自己否决：

```
span-degenerate 5→3    但   text-damage 1→2    verified 1824→1823
```

它修好了两个、弄坏了一个、总分下降。**"数字动了"不构成保留理由**——这与 L-04 是同一条原则,
只是这次要否决的是自己刚写的东西，心理成本更高。

**教训**：验收判据要在**看数据之前**定下，否则会事后合理化。
本项目后来把这条写成了硬约束：任何修复必须同时不使**两个**闸门回退。
