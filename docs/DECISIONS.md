## D-001 文档解析：PyMuPDF 主 + markitdown 交叉校验，分歧即质量闸门

**状态**：采用（已实测）

**背景**：10 份真实中文 PDF 中 4 份文本层不可信。根因是 subset-embedded Identity-H
CID 字体缺 ToUnicode CMap（CNKI `ReaderEx_DIS` 是惯犯），提取时不抛异常、不报警告。

**关键实测**：两个引擎的失败方式相反，而不是一个好一个坏。

| | PyMuPDF 1.28.2 | markitdown 0.1.7 |
|---|---|---|
| 坏字体输出 | `地方䎟府税收竞䎚` 貌似合理的错字 | `地方(cid:17311)府税收竞(cid:17306)` 显式占位 |
| 失败模式 | **静默污染** | **响亮失败** |
| 页边界 | 保留 | **0 个**（4 份 PDF + 1 份 EPUB 全部为 0） |
| 速度 | 0.30s / 35页 | 13.3s / 35页；110.8s / 53页扫描件 |
| 表格 | 丢结构 | 重建为 markdown 表格 |
| 扫描件 | 0 字符 | 0 字符（白耗 110 秒） |

正文词频两者一致（税收 632/630、竞争 582/580），证明**没有任何文本层提取器能修复
坏 CMap**，OCR 是唯一出路。

**决策**：PyMuPDF 作主解析器（要页码、要速度）；markitdown 作交叉校验与表格/EPUB
兜底；**两者分歧的字符判为不可信** → 隔离 → 转 OCR。两个独立解析器免费换来一个质量闸门。

**踩过的坑**：`(cid:12977)` 是 ASCII，纯 PUA/Ext-A 码位普查会把 markitdown 判成
0.00% 干净。这是度量假象。任何 junk 检测必须同时统计 `\(cid:\d+\)`。

## D-002 引用基座：Kanripo；Gutenberg 仅作校验源

**状态**：采用（已实测）

**实测对比**（同为繁体《周易》，两次独立数字化）：

| | Kanripo KR1a0001 | Gutenberg #25501 |
|---|---|---|
| `<pb:>` 页锚点 | 1,077 | **0** |
| 《X第N》卦标题 | 64 | **0** |
| 净字数 | 21,789 | 37,480（1.72×） |

Kanripo 的 `<pb:KR1a0001_tls_001-5a>` = 版本+卷+叶+正反面，是可核验的引用锚点，
且不需要 API key。这直接解决"如何引用古籍而不编造页码"。

Gutenberg 零锚点 → **只能当校验材料，不能当引用基座**。但它作为独立数字化版本，
能低成本发现真实分歧（见 D-003）。

**备用**：daizhigev20（量大，188 个易类文件，含伊川易傳、朱熹本義）——无页码标记、
**无 license 文件**，法律状态不清 → 可作语料，不可作引用基座。

**暂不采用**：ctext.org 全文。`gettext` 返回 `ERR_REQUIRES_AUTHENTICATION`，需 API
key / 注册 IP。元数据 API（`gettexttitles` 等）开放，3.8 MB 标题表可作书目交叉参考。

**已知法务缺口**：**25 个 Kanripo 仓库中，没有一个包含 LICENSE 或 COPYING 文件**。
底本是前现代文献，但数字化本身未声明条款。按 work 逐条记录，不假定宽松许可。

## D-003 異體字折叠：必须做，且必须在索引与查询两端做

**状态**：采用（已实测两类独立证据）

**证据一，同一部书内部混用**（KR1a0007）：傳 118 vs 𫝊 96 → 搜「傳」漏 45%。
更糟：玄 0 vs 𤣥 73、弘 0 vs 𢎞 66 → 搜「玄」返回**零**。另有 說/説 342/260、
內/内 1/305、類/𩔖 113/105。单一部书内 549 个星平面字符（>U+FFFF）。

**证据二，跨来源系统性相反**（本次新增）：

```
無/无:  Kanripo    2/299      Gutenberg  302/0     ← 约定完全颠倒
風/风:  Kanripo   19/0        Gutenberg   19/0     ← 一致
觀/观:  Kanripo   50/0        Gutenberg   50/0     ← 一致
```

后果可直接观测：`見群龍无首` 在 Kanripo 命中 1 次，在 Gutenberg **命中 0 次**——
文本并不缺失，它写作`見群龍無首`。这比证据一更棘手：每个来源各自内部自洽，
但彼此冲突，所以"用干净的现代繁体源就没事"是错的。

**NFKC 无效**：`unicodedata.normalize("NFKC", ...)` 对测过的每一组都原样返回，
只有完全相同的码位才会合并。→ 手工维护折叠表是硬需求，不是优化项。

**决策**：折叠表在**索引时和查询时都应用**。表的构建方式是**对比来源自动产出候选**
（Kanripo vs Gutenberg 的差异就是免费的候选集），而非凭空枚举。

**另需处理**：Kanripo 用 `&KR0658;` 形式表示无 Unicode 码位的字形，每部书 22–31 个
（约占 0.01–0.03%）→ 需占位符语义，不能静默丢弃。

## D-004 全文检索：SQLite FTS5 + 逐字切分

**状态**：采用（已实测）

FTS5 默认 `unicode61` 分词器对 1–2 字中文查询**静默返回空结果**。逐字切分后
（把每个 CJK 字符用空格隔开再入索引）「君子」这类查询才能命中。

**决策**：SQLite FTS5，入索引前逐字切分 + 折叠異體字。理由：零运维、单文件、
7.4 GB 内存机器上不需要额外进程。

**暂不采用**：Elasticsearch / OpenSearch（无 Docker，JVM 内存开销在 7.4 GB 机器上
不合理）。若将来书量到几千部再重新评估。

## D-005 版本对齐：用作品内在地址，不用页码

**状态**：采用（已实测），但**具体算法未达标**，见 D-006

**实测**：三个本子 `BASEEDITION` 不同（tls / SBCK / WYG），卷号体系互不兼容
（1–69 / 1–10 / 0–41），同一段话出现次数都不同（潛龍勿用：5 / 3 / 12 次）。

→ `<pb:>` 是**引用**锚点，不是**对齐**键。对齐必须用作品内在地址（周易的情形是
卦 + 爻位，如 乾卦·九三），即每部作品一套 canonical reference scheme。

**新增素材**：`KR1a0031 原本周易本義` 与 `KR1a0032 別本周易本義` 是**同一著作的两个
版本**（15 文件/85,427 字 vs 5 文件/88,238 字，同为 WYG），是现成的多版本测试集。

## D-006 卦/爻 属性还原：已解决，97.3%

**状态**：采用（已实测）。实现于 `src/guji/{variants,anchors,zhouyi}.py`，
打分脚本 `scripts/validate_alignment.py`，诊断脚本 `scripts/diagnose_yao.py`。

### 先前的错误判断

我一度断定「注疏的显式卦标记为 0%」。**这是错的**，原因是我只匹配了 KR1a0001 的
`《X第N》` 格式。实际上每部注疏都带 **Unicode 卦符 U+4DC0..U+4DFF**，按王弼序排列，
`卦號 = 码位 − 0x4DC0 + 1`。

基于错误前提的「尝试一」（从正文抽 512 条唯一短语、顺序扫描沿用最近卦名）因此被废弃。
它的覆盖率 84.3% / 80.3% 看着可用，但漂移 max 610 单元，且有实证错误：一个被标为
「乾」的单元内容是 `坤三以處下卦之上故免龍戰之災`，实际在讲坤。

### 现方案

**两个互相独立的键。** 卦符，加上八卦组合注 `(乾下/乾上)`。映射由语料邻接关系推导，
不硬编码：64 个八卦对 → 64 个卦符，**零碰撞**。爻的阴阳极性也由同一批注推出，因此
爻位名是**算出来的**（乾 → 初九…上九 + 用九）而非写死。64 个卦符中 27 个的注有冲突，
几乎全是八卦名的異體字（兊/兌/兑、巽/㢲），多数票解决；其中一个是真实源文错误
（卦12 注作 `良下震上`，而「良」根本不是八卦名）。

**分段必须用最长严格递增子序列（LIS），不能用贪心的开头递增段。** 差距是决定性的：

| 语料 | 贪心 | LIS |
|---|---|---|
| KR1a0007 注疏 | 18 段 | **63** |
| KR1a0031 / KR1a0032 本義 | 各 1 段 | **各 63** |

贪心在两处真实情形上失败：KR1a0007 有源文错字（卦52 夹在 17 和 19 之间），贪心接受它
并把水位抬到 52，随后把真正的 19..51 全判为回退；KR1a0031/0032 把朱熹的**卦變图表区
排在正文之前**，根本不存在开头递增段。LIS 无需为二者写特例。严格递增顺带消除了重复卦号。

**爻级必须锚定爻辭原文，不能锚定爻位标记。** 两个实测理由：
KR1a0007 的乾卦跨度内出现 六二、六五，而乾卦六爻全阳、不可能有阴爻——那是孔穎達交叉
引用别卦的爻；另外在 `初九潛龍勿用九二` 中，`用九` 会跨 `勿用`+`九二` 误匹配，截断前一条
爻辭。故按 canonical 顺序逐个搜索，每个标记只在前一个之后查找。

**对不上的一律标 `unknown`，不猜。**

### 打分

Gold set 从 KR1a0001 自动抽取，不手写（手写版错过两次：屯六二漏 `匪寇婚媾`，且爻位写成
六五/上九，而屯是震下坎上、实为九五/上六）。

```
合计 85.6% → 97.3%  (1821/1872)
KR1a0006 98.4%   KR1a0007 97.9%   KR1a0016 98.1%
KR1a0031 93.6%   KR1a0032 98.4%
覆盖率：KR1a0007 与 KR1a0032 均 380/380，unknown 归零
```

提升全部来自**用诊断输出扩充折叠表**（两轮共 45 对）。最高频的一对 `苞/包`（19 次）
在第一轮完全不可见，因为分类器要求 3 字匹配前缀才判为变体，把所有第 0 位替换都归进了
`absent`。

### 剩余 51 个失败中，15 个是 `differs` —— 这是特性，不是缺陷

那是版本间的真实異文（通假字：`枯楊生稊/生梯`、`跛能履/破能履`）。这些必须作为**校勘
证据保留**，绝不能折叠抹平。这正是 Work 与 Edition 分开建模的收益所在。

### 待办

- KR1a0031 的 93.6% 未过 95%，需单独查
- `outside` 桶目前把**十翼交叉引用**和**卦變图表**混在一起（KR1a0031/0032 各 125 个）。
  卦變图不是噪声，它表达卦↔卦变换关系，应是**独立的单元类型**，需三分而非二分

## D-008 单元边界：先按地址切，再按层分，最后合并

**状态**：采用（已实测）。`src/guji/ingest.py`

Kanripo 的 `¶` 是**刻本物理行界**，不是语义边界，它会落在任何位置——包括词的中间：

```
KR1a0006 的九二爻位标记存作：  '九¶\n二見龍在田'
raw.rfind('九二') → -1        标记存在，但原文里找不到连续形式
清洗视图 offsets[12]=26, offsets[13]=29   清洗后相邻，原文里隔 3 个字符
```

**由此得出三条硬规则：**

1. **任何标记匹配都走清洗视图，再经偏移表映射回原文。** 绝不在原文里「重新查找」标记去
   校正偏移——对九二这种被劈开的标记必然失败。
2. **单纯按 `¶` 切分会把段落切碎。** 实测：王弼的乾九三输出为 `日乾乾夕惕若厲无咎`
   （丢了「君子終」），朱熹的输出为单字 `咎`。修法是合并 (file, layer, 卦, 爻) 相同的
   连续单元。单元数 167,146 → 35,978，文本变得可引用。
3. **一个 `¶` piece 可能跨越爻边界**，必须先在地址边界处切开再归属，否则前半片会被归给
   上一个爻。

~~**残留已知缺陷（外观）**：单元开头会落在爻位标记的第二个字（`三君子終日乾乾…` 而非
`九三君子終…`）。地址归属与爻辭本身都正确，只有标记首字落入上一单元。不再追查~~

**⚠ 上面这段结论是错的，已由 D-011 推翻。** 它不是外观问题，是同一个偏移错位的两个症
状之一，另一个症状是**向引用文本里注入了原文没有的字符**。「不再追查」这个判断本身就是
本项目至今最严重的一次误判：一个引用系统伪造引文，而计数型检查完全看不见。

规则 1（不得在原文里重找标记）依然成立且必须坚持——修法不是去重找，而是**带着偏移表走**。

**合并上限 900 字**：一个卦的疏可超过 8 万字，命中结果必须可引用，所以设上限；保留的页
锚点是**第一个**，即段落开始处。

## D-009 十翼与卦變圖是独立单元类型，不是噪声

**状态**：采用（已实测）。`anchors.classify_offchain()`

LIS 把不在链上的卦符全丢进一个桶，但里面实际有**三类**，判别信号都是实测出来的：

| 类型 | 判别依据 | 含义 |
|---|---|---|
| `圖` | 卦符密度（±60 字窗口内 ≥4 个） | 朱熹卦變圖，表达卦↔卦变换关系 |
| `正文` | 符号后紧跟 `(X下Y上)` 八卦组合注 | 被 LIS 丢弃的正文注解 |
| `十翼` | 其余 | 繫辭/說卦/序卦/雜卦 的散文引用 |

实测分布（KR1a0006 / 0007 / 0016 / 0031 / 0032）：
圖 0/0/0/124/124 · 正文 2/1/3/1/1 · 十翼 13/11/0/0/0。

**为什么密度而非 gap 长度**：KR1a0031 的图表是 `䷖剝䷇比䷏豫䷎謙䷆師…` 这样的密集
「符号+卦名」对，113/125 的 gap ≤ 12 字；而 KR1a0006/0007 的 table-like 计数为**零**，
其 off-chain 符号 gap 在 25–2400 字之间且读起来是散文。图表的说明文字
（`凡三陰三陽之卦各二十皆自泰否而來`）属于同一张表。

**顺带修掉的真实归属错误**：LIS 最后一个 span 原本延伸到文件末尾，于是十翼散文被当作
「卦64 的注解」。现在末段止于第一个 off-chain 符号。

**核查结论**：`lost 卦` 全空——没有任何卦因 LIS 丢弃而完全缺失，off-chain 正文都是已在
链上卦的重复出现。这条必须核查，否则「三分」可能掩盖真实的覆盖损失。

## D-010 FTS5 短语匹配必须显式加引号

**状态**：采用（已实测）。`search.fts_phrase()`

逐字切分把一个 CJK 查询变成多个 token，而**裸的多 token `MATCH` 是隐式 AND**，命中范围
是整个文档。搜 `見群龍无首` 会命中任何同时含这五个字的单元，不论顺序与位置。
把切分结果加引号才是短语匹配。

**这个缺陷无法用命中计数测出来**——计数型测试在 AND 语义下照样通过。验收测试必须断言
**返回文本**确实包含目标短语。`scripts/verify_index.py` 的 12 项断言全部基于返回文本。

## D-011 偏移必须随文本一起传递；「清洗后的文本 + 原文起始偏移」是伪造引文的根源

**状态**：采用（已实测）。`ingest.Piece`、`probes/probe_skew.py`、`probes/probe_conservation.py`

**这条推翻 D-008 的「残留缺陷是外观问题」。**

`_iter_pieces` 旧实现返回 `(原文起始偏移, 清洗后文本)`，调用方却用原文坐标去索引清洗后
文本。Kanripo 的分隔符是 `¶\n`，所以**每个 piece 都以换行开头，错位恒 ≥ 1**；piece 内含
`<pb:>` 时错位可达 14。

```
错位 piece 占比：6233/6233、9478/9478、7748/7748 …  = 100%（8 部易類全部）
被放错的地址切点：2,634
爻单元以自身爻位标记开头：0 / 1872        ← 修复后 1858 / 1872
```

**两个症状，同一个根因**：

| 症状 | 旧判断 | 实际 |
|---|---|---|
| 单元从标记第二字开始（`三君子終日`） | 「外观」 | 症状 A |
| `有能乾○九乾惕厲之象`（原文为 `有能乾乾惕厲之象`） | 未发现 | 症状 B：**伪造引文** |

泄漏的首字被带进**上一个**单元，且落在该单元的注文**之后**，于是引文里出现了原文那个
位置上根本没有的字。这类缺陷计数型检查一律看不见。

**修法**：`Piece` 携带 `offsets[i] = text[i] 的原文偏移`，任何原文位置一律 `bisect_left`
换算成文本下标。**绝不**回到原文里重找标记（D-008 规则 1 仍然成立）。

**顺带修掉两个同源缺陷**：

1. **层次语义塌陷**。旧代码每部书只有一个 layer，于是王弼/程頤/朱熹三家被引的**經**和
   他们自己的**注**同标为 `注`；`--layer 經` 只能捞到 KR1a0007。更糟的是 `merge_units`
   因 `(file, layer, 卦, 爻)` 相等而把經与注**融成一块**，文本次序被打乱。现按 piece 内
   位置顺序交替发出 `經`/`注`（括号内外），`經` 命中数 3 → 10。
2. **`gua_name` 是死字段**，全部写成 `""`。现从 KR1a0001 的 `《X第N》` 标题推导（64 个齐全）。

**守恒验收**（`probe_conservation.py`）：单元数 35,978 → 8,611（跨注合并所致），但

```
28 部 CJK 字符：源 2,653,857  索引 2,653,857   delta 0   缺失 0   凭空多出 0
重复率 1.0000        raw_start..raw_end 越界单元 0 / 4985
```

单元数变化本身分辨不出「合并」与「丢数据」，所以这个多重集守恒检查是必需的闸门，
不是可选项。

**`max_gap=400`**：合并改为按 key 跨注合并（經 的上下半句被中间的注隔开），必须限距，
否则相隔数千字的两段会融进同一单元，而其 `raw_start..raw_end` 就不再描述连续原文——
那就是不可核验的引用。

## D-012 语料本身有 OCR 损坏；质量闸门必须用独立见证，不能用表面统计

**状态**：采用（已实测）。`src/guji/quality.py`、`scripts/check_quality.py`

**本项目一直把 Kanripo 纯文本当作干净的 ground truth。这个假设是错的。**
KR1a0006 卦61 中孚 的一段被 OCR 破坏，而**没有任何环节能发现它**：

```
KR1a0006  上九翰青登于天貞凶輪高飛也狀音堵昔莊而寳才從之謂也届卦之上處信芝絃信終剛唐志罵內喪筆美外揚
KR1a0007  上九翰音登于天貞凶注翰高飛也飛音者音飛而實不從之謂也居卦之上處信之終信終則衰忠篤內喪華美外揚
```

青/音、輪/翰、届/居、芝絃/之終、筆/華 —— 全是形近替换，即 D-001 里那个 OCR 特征，
但这次出现在**根本不含 CID 字体的纯文本源**里。同一部书的 卦19 臨 另有缺文
（335 字 vs 注疏 1804 字，初九/九二/六三 三爻整段缺失）。

### 两个探测器，失败的那个更有信息量

**表面稀有度（字符 bigram 不可信度）—— 失败，且是本轮唯一的负结果**

```
已知损坏窗口排名 599 / 88,530（低于自身 99.5 分位阈值 0.424，hapax 仅 0.390）
榜首全是假阳性：太玄經的音義字表「廬偈音傑…音吪動也」
```

文言文的音義字表、人名地名表天然充满未见 bigram，与 OCR 垃圾在表面统计上不可区分。
**这个函数保留在 `quality.py` 里，标注为负结果**，避免以后有人再想一次。

**跨版本一致性 —— 通过**

KR1a0007 註疏 逐字包含 王弼注，所以在同一 卦·爻 地址上两者应近乎一致：

```
358 个共享地址   coverage 中位数 0.991   均值 0.965
已知损坏窗口排名 2 / 358，coverage 0.050，contiguity 0.072
```

**关键：它不需要新基础设施**——所需的 卦/爻 连接键本来就为 D-005 存在。

### 判据必须是 contiguity，不是长度比

第一版按长度比判定，把 卦61 误判为「B 段退化」，因为 lenB=83 < lenA×0.2。
实际 B 才是正确长度，是 **A 段过长**：A 吞掉了 卦62，因为该版把 卦62 的符号误刻为
`䷋`（卦12）——正是 D-006 记录过的那个源文错字，于是 LIS 丢弃它，段落顺延。

```
contiguity = 最长公共子串 / 较短文本长度
  散碎短匹配（<0.25）→ 逐字替换 = OCR 损坏
  一长段 + 长尾      → 文本一致，只是某段覆盖更广
```

实测判定（8 个低 coverage 地址）：`text-damage` 1 · `span-overextended-A` 2 ·
`span-degenerate-B` 5。

### 顺带暴露我自己的缺陷：5 个「已定位但其实错位」

`span-degenerate-B` 那 5 个（卦46九二 lenB=1、卦9初九 lenB=6、卦58九五 lenB=9 …）是
**我的抽取错误**：KR1a0007 里有序爻位搜索锁定了孔穎達的交叉引用而非真正的爻辭，段落因此
只有几个字。而 `validate_alignment` 把它们统计为 **located**——

**覆盖率指标恰好看不见这一类错误。** 这就是为什么必须有一个不依赖 gold set 的独立闸门。

### 已知局限（不掩盖）

卦64 的最后一个地址会吸收 十翼 尾部，而各版 十翼 编排不同（31,523 vs 14,402 字），
是段落终点的产物而非损坏，故显式排除。这个排除只对**这一个已知地址**成立。

### 控制组是强制的

`check_quality.py` 若检测不到 卦61 即 **exit 1**。没有已知阳性对照的质量闸门等于没有闸门——
稀有度探测器就是被它否掉的。

## D-013 折叠候选必须过语料频次否决；分数不是理由

**状态**：采用（已实测）。`variants._DIAGNOSED_3`、`NOT_VARIANTS_3`

KR1a0031 停在 93.6%，用同位置对比姊妹版 KR1a0032 产出 8 个折叠候选。**只有 3 个通过。**

否决理由全部是语料频次——折叠是对**语料和查询的全局重写**：

| 候选 | 变体数 vs 正字数 | 否决理由 |
|---|---|---|
| 極→拯 | 2,821 vs 163 | 比值 17.3，语境是 **太極**/極深/無極。为一个爻（渙初六 用拯馬壯）把全语料的 太極 改写掉 |
| 悔→晦 | 1,136 vs 538 | 語境是 **亢龍有悔**/无悔/悔亡，悔是周易核心词。KR1a0031 明夷初九 印作 悔 是**源文误刻** |
| 其→有 | 24,061 vs 31,266 | 汉语最常见的两个字，荒谬 |
| 昊→昃 | 37 vs 32 | 昊 在别处是正确字（**昊天**、陽氣昊大），折叠会破坏正确用例 |
| 冽→洌 | 9 vs 16 | 全部语境都是 井洌寒泉 这一句；冽（寒）洌（清）是两个词，属**校勘证据**，与 梯/稊、破/跛 同类 |

通过的 3 个，每一个的全部语料语境都指向正字：`眀→明`（王眀/義眀）、`𠖇→冥`（𠖇升/昬𠖇）、
`収→收`（井収/教収歛）。

**结果 93.6% → 94.4%，仍未过 95%，且我不再去追它。** 剩余失败已逐条定性：
源文误刻、真实異文、以及 3 个下面 D-014 的爻位误标。**把分数刷到 95% 需要接受
`極→拯` 这类折叠，那是用语料正确性换指标。**

`FOLD` 与 `NOT_VARIANTS` 现在在 import 时互相校验，两表不可能再各说各话。

## D-015 通用性证伪测试：schema 把一种作品的地址体系写成了列名

**状态**：已证伪并已修（见 D-016）。`probes/fetch_generality_set.py`、`probes/probe_generality.py`

28 部全是中文古籍，所以「通用书籍研究基础设施」这个说法此前**无法证伪**。最薄弱处不是
门类覆盖，而是**只实现过一种正典地址体系**（卦 + 爻位）。于是取 10 部公版西文书专攻这一点：

| tier | 目的 | 作品 |
|---|---|---|
| 1 | 同一作品 + 多独立见证 + 共享地址 | KJV / WEB / Douay-Rheims 三个圣经译本；Iliad 两个译本 |
| 2 | 地址形状完全不同 | Plato（Stephanus）、Shakespeare（幕/场）、Euclid（卷/命题） |
| 3 | 本无正典地址 | Darwin、Herodotus —— 只应有页/偏移锚点，与術數类同 |

### 结论一：schema 结构性不通用

```
unit 列: id work_id file raw_start raw_end page_anchor gua gua_name yao layer text
可用于 book/chapter/verse 的列: 无
```

`gua/gua_name/yao` 是**字面列名**。第二种地址体系**根本无法存储**。这不是「再加几本书」
能解决的，是结构问题。

### 结论二：三种失效模式在完全不同的语料上原样复现

这比结论一更有价值——说明 D-006 学到的东西是可迁移的：

**（a）沿用最近标题 = 貌似合理的错答**。探针里随手写的「跟踪最近书名」逻辑给出：

```
查 Psalms 23:1  → 返回 以賽亞書 23 章的文字（Howl, ye ships of Tarshish）
查 John 3:16    → 返回 啟示錄 3:16 的文字（thou art lukewarm）
```

**和 D-006「尝试一」一字不差的同一类错误**：覆盖率好看、答案是错的。当时的解法是改用
**作品内在且可自校验的键**（卦符按王弼序 → 卦號）。圣经的对应物同样存在：66 卷书名是
**有限且有固定次序**的，所以同一套 LIS 方法可以照搬。

**（b）交叉引用被当成地址**。Douay-Rheims 行首 `C:V` 只有 **3** 个，而行内 `C:V` 有
**35,905** 个——后者是**旁注互见**（`23:30 / 2 Par 36:1`）。与 十翼 反复引用别卦、
孔穎達在乾卦内提到六二 完全同类。天真的经文号解析器会把互见编成地址。

**（c）版本自带的标记法互不兼容**。同一部书三个译本：KJV 行首 `1:1 `，WEB 行首
`001:001 `，Douay 经文号在行内。与三个周易本子 `BASEEDITION` 卷号体系不兼容（D-005）
是同一件事。

**因此 D-005/D-006 的结论不是周易特例，而是可复用的地址层设计约束。**

## D-017 见证分三级；能化为「与字形无关的结构量」的见证最强

**状态**：采用（已实测）。`probes/probe_external_witness.py` 等四个探针

核查五个外部 GitHub 周易项目,目的不是取代码,而是给我们**全部由语料推导**的卦表找独立见证。
推导式设计是对的,但有一个盲区:**系统性推导错误完全不可见**,因为所有下游检查继承同一假设。

### 最高价值：极性 64/64 吻合

`Ovilia/biangua` 的 `gua.json` 每卦带一个六位极性串（乾 `111111`）。

```
我们（从语料八卦组合注推导） vs biangua（独立产出）：64/64 全部一致
```

**位序约定先手验证,不假定**:屯 = 震下坎上 → (1,0,0)+(0,1,0) = `100010`,biangua 亦 `100010`;
蒙 = 坎下艮上 → `010001`,一致。两个非对称卦确认下到上。

### 由此得到一条推论，价值超过验证本身

极性是**纯位串,与简繁/異體完全无关**。既然 64/64 吻合,biangua 第 N 项**就是**我们的卦 N。
**因此后续任何名称差异都只能是正字法或命名约定,不可能是映射错误。**

这让 28 行名称差异的审查成本骤降:26 行是纯简繁（訟/讼、謙/谦…）不必处理,只剩 2 行需实查,
且两条都查在我们这边:

| 卦 | 我们 | biangua | 查证 |
|---|---|---|---|
| 29 | 習坎 | 坎 | KR1a0001 原文印《習坎第二十九》→ **我们对**（该版正名） |
| 33 | 遯 | 遁 | 语料 遯 22/59/142/39 vs 遁 0/0/2/1 → **我们对** |

### 见证分级

| 级别 | 例子 | 能做什么 |
|---|---|---|
| **无关字形的结构见证** | 极性位串、序号、计数 | **判对错**,且免受正字法干扰 |
| 同址跨版本文本见证 | KR1a0006 ⊂ KR1a0007 | 判对错（D-012） |
| 跨来源正字法见证 | Kanripo / Gutenberg / sunls2 | **只能产折叠候选,不能判对错** |

**设计启示**:凡能化为与字形无关的结构量的东西,优先用它做见证。

### 顺带产出一个折叠：於 → 于

`sunls2` 印 `需於郊`,我们底本 `需于郊`——一个字,导致 298 条 gold 爻辭头有 75 条找不到（74.8%）。
按 D-013 的频次否决流程审:

```
全语料 於 12,198 / 于 2,862,且方向逐版本颠倒（KR1a0001 於53/于120,KR1a0007 於2121/于497）
每个 於-复合词都有 于 版本： 於是106/于是14 · 至於450/至于150 · 在於261/在于12 · 見於157/見于27
爻辭 几乎只用 于： 需于郊 13/0 · 龍戰于野 18/1
```

**双向共存是它与 `極/拯` 的分界**:那是两个词,这是一个词的两种写法。折叠 `於→于`。

**已知代价,明写**:`於乎`（叹词,非介词）1 次会变 `于乎`。`于乎` 本身是该叹词的既有写法,
1 次对 12,198 次可接受——但它**是**代价,不是零。

实测:对齐 1824/1872 **不变**,验收 ALL PASS,质量 PASS,守恒 1.0000。
**分数不变不代表无收益**——收益在跨来源检索,单独验证:查 `需於郊` 现能命中 `需于郊`,
两种写法命中数相同。

### LIS 不是可迁移的洞见

`gua_spans()` 用 LIS，在易類上从 18 段提到 63 段，成绩很好。但用在京氏易傳上只得
**12/62**——不是格式不兼容（版式与易類相同），而是 **LIS 编码了王弼序，而此书按八宮排**。

**可迁移的是「用作品自身的排序原则」，不是 LIS。** 排序原则必须逐部判定。

### 但「按符号编址」这个替代方案也被实测部分推翻

去掉 LIS、逐符号编址可达 59/62（95.2%），而那 3 处失败是关键：

䷷巽下離上鼎…    ䷷=卦56 旅， 文字「鼎」    鼎=卦50，符号与内容不符

后两条是**真实的符号/内容错配**，很可能是数字化时机械插入符号所致。
**故在此书中卦名比卦符可靠：编址应以卦名为主、卦符为校验**，并把错配报告为源文异常
（照 D-014 的做法）。

### 焦氏易林的结构尚未查明，不要沿用猜测

我曾写下「4,032 个 本卦×之卦 配对，邻接率 96.8%」——**这两个数字是没测就写的**。实测：

（`addr1=本卦, addr2=之卦`），这是 D-016 通用形状的回报，但具体解析器要先查版式。

## D-019 G1 评测集：题库从 `data/raw/` 派生，且打分前逐条回查原文

G1 判据是「给定概念，返回的原文片段人工核验准确率 ≥ 95%」。要把它变成一条可执行命令，
关键不是题目多少，而是**gold 从哪来**。比较过三个方案：

| 方案 | 结论 | 依据 |
|---|---|---|
| A 手写题目与答案 | **否决** | 本项目手写 gold 已错过两次：屯六二漏 `匪寇婚媾`；屯的爻位写成 六五/上九，而屯是 震下坎上，应为 九五/上六。手写量也上不去 |
| B 从索引派生题目、再拿索引验收 | **否决** | 循环。索引就是被测对象，系统性缺陷会被写进 gold 然后自我印证——这正是 X-07：索引产出 `有能乾○九乾`（原文 `有能乾乾`），而**所有计数型检查都通过** |
| C 从 `data/raw/` 派生，回查 `data/raw/` | **采纳** | 每条 gold 都是一个在**具名源文件里被证明存在（或被证明不存在）**的字符串。索引只当答题者，永不当裁判 |

落地：`scripts/derive_eval_g1.py` → `data/catalog/eval_g1.json` → `scripts/eval_g1.py`。
`eval_g1.py` 打分前**独立重读 `data/raw/`** 逐条复核 gold；不成立的题报 `INVALID` 并
排除出计分，**绝不静默通过**。判据在看结果之前登记在 `eval_g1.py` 顶部（top-10；
七类各自的目标值），其中 `grounded_neg` 与 `citation` 是 100%，不接受任何放宽。

### 一个必须分开的细节：三种归一化空间

派生与复核如果各自实现"同一段文本"，就会重演 L-01 的折叠表双拷贝。因此空间定义收进
`src/guji/evalset.py`，两个脚本都从那里导入。三种空间**不可互换**，每一种都是被实测逼出来的：

```
folded_notes    折叠 + 保留注   通用比较空间；证明"伪造串不存在"必须用它（要覆盖注文）
folded_jing     折叠 + 去掉注   爻辭 gold 的派生空间。经-only 视图里的串一般**不是**
                               保留注视图的子串：原文 「AB(注)CD」 的經视图是 ABCD，
                               而它在保留注的视图里根本不出现 —— 6 道 version 题因此曾报 INVALID
unfolded_notes  不折叠 + 保留注 折叠类题目必需：fold() 把 黄 映射成 黃，所以在**任何**折叠空间里
                               变体字都不存在，「黄 是否出现在 KR1a0006」永远只能答"没有" —— 2 道题因此曾 INVALID
```

### 结果与一条自我约束

193 题全过（`retrieval 40/40 · retrieval_cross 24/24 · retrieval_hard 24/24 ·
citation 30/30 · grounded_pos 25/25 · grounded_neg 30/30 · version 20/20`）。

**但 G1 记 PART，不记 PASS。** 题库的每道题都锚在语料中逐字存在的文本上，证明的是
逐字与结构层面的能力；G1 字面要求的**概念级**检索没有覆盖，FTS5 也覆盖不了。
按 PASS 上报，与 G8「只有 Source 表所以隔离成立」是同一种虚报。

同理，`eval_g1.py` 会自己打印 rank 分布并在某一层 rank 全同时**主动印出"该层不具区分度"**：
`retrieval_cross` 24 题 rank 全为 1。**100% 不是"做对了"的证据，先怀疑题目太容易**（§2）。

## D-020 `addresses_of` 的窗口口径：跨版本闸门此前对 KR1a0031/0032 近乎空转

做 T1 的 version 类题目时，从 `data/raw/` 数出 31/32 有 377 个共享地址、47 个在爻辭内部
就有分歧；而 `check_quality.py` 印的是「**17** shared addresses, 中位覆盖 1.000,
低于 0.60 者 **0**」。两个数不能同时成立，于是去查（`probes/probe_addresses_fix.py`）。

**根因**：`addresses_of` 的窗口止于「下一个爻位标记前最后一个**經**字符」
（`r1 = jing.origin(end - 1)`），再拿这个窗口去**保留注**的视图里取字。于是：

* 注被括号包住的版本（KR1a0031/0032）：注文全部落在窗口外 → 一个地址只剩爻辭，中位 **9 字**；
* 注以字面「注」字排版的版本（KR1a0007）：注文本来就在經视图里 → 中位 **102 字**。

同一个函数在不同版本里**含义不同**，而它的 docstring 对两者都写「經+注 text」。
后果是 `cross_edition_coverage` 把 377 个共享地址中的 **360 个**丢给自己的
`min_len=20`，然后对剩下 4.5% 报出满分。**这不是 G3 的证据。**

**改法**：窗口从本爻位的原文偏移取到**下一个爻位的原文偏移**（末爻取到段尾），
即"两个爻位之间印的一切"——跨版本比较要有意义，这才是"该地址上的文本"。

先定后测的验收判据（三条）与实测：

| 判据 | 结果 |
|---|---|
| 31/32 参与比较数 17 → **>300** | **373**，中位覆盖 0.985 |
| 06/07 保持 ≥358 且中位覆盖 ≥0.95 | **362**，中位 **0.991** |
| 卦61上九 仍判 text-damage（已知阳性对照） | **仍触发**，coverage 0.070 contiguity 0.034 |

八道闸门零回退（对齐仍 1824/1872），故采纳。附带两个产出：

1. 31/32 新暴露 **卦23六四 / 卦61初九** 两个离群地址，**正是** `detect_mislabelled_yao`
   已独立标为 KR1a0031 爻位误刻的同两个地址（D-014）——两个互不相干的探测器互相印证。
2. 06/07 的 **卦47上六** 由 `span-overextended-A` 改判为 **`text-damage`**
   （contiguity 0.199，lenA 845 / lenB 462），即语料里**可能有第二处 OCR 损坏区**。
   已记为待办 P-01，**不在本条里下结论**。

## D-021 差异摘要必须分类而不是归并；并且需要两条比较轴，不是一条

G5 缺的一直是「差异摘要」。做法上唯一的硬约束来自 D-013：`differs` 類異文
（`枯楊生稊/生梯`、`跛能履/破能履`）是**校勘证据**，摘要**不能**把它们抹平。
所以摘要的输出不是"相同/不同"，而是**分类**，且类别**从折叠表读出**、不靠猜：

| 类别 | 含义 | 来源 |
|---|---|---|
| `preserved-variant` | 该字对在 `NOT_VARIANTS` 里——**曾经考虑过折叠并被否决**，附当初理由 | `variants.NOT_VARIANTS` |
| `orthographic` | 两读折叠后相同（`濳/潛`、`黄/黃`）。**照实报出**但注明非異文 | `variants.FOLD` |
| `divergent` | 折叠后仍不同且无记录。**本模块不判定谁对** | — |
| `omission` / `addition` | 一方多出/缺少一段共享文本 | — |
| （注文） | 只报**体量**，不做字符级 diff | `COMMENTARY_MARKS` |

### 两条轴，这是被对照逼出来的修正

初版把六个见证全部对**底本**做 diff。对照集里 `卦1九三 居卜之上/居下之上` **报不出来**，
而且是**结构性报不出来**：它是 朱熹《本義》两个版本在**他自己注文**里的差异，
底本根本没有注文。**「所有见证对齐到一个参照」对同一著作的两个版本是盲的**——
而那恰恰是 Work / Edition 分开建模要暴露的东西（D-005）。现在两条轴：

* **注家轴**（默认，`layer='經'`）：不同注家只共享 經，所以只比 經；
* **版本轴**（`EDITION_PAIRS`，`layer=None`）：同一注家的两个版本，注文也是共享文本。

### 另外两条初版做法被对照否决

1. **逐字 diff 不同注家的注文** → 产出一条 350 字的"差异"。不同注家本来就各说各话，
   这不是发现。改为注文只报体量（`KR1a0007=853字`）。
2. **在带标点的空间里比较** → KR1a0001 是唯一大量施标点的版本，`稊` 被切成 `'稊，'`，
   不成字对、无法分类。改为在 `unfolded_notes` 空间（去标点、**不折叠**）比较。
   **不折叠是关键**：一旦先折叠，正字法差异会从对齐里整体消失，摘要就再也无法告诉读者
   该见证印的是 `濳` 而非 `潛`——那等于用"看起来一致"换掉了信息。

### 闸门与实测

`scripts/summarise_diff.py` 带对照集，失效即 exit 1（照 L-03）。四条正向对照全过；
两条**反向义务**是这个闸门真正的价值所在，因为它们守的是"静默毁证据"这一侧：

```
A  75 条 divergent 读法，折叠后相同者 0        （正字法差异不得被报成異文）
B  全 386 个爻地址、2,821 条 orthographic 读法，NOT_VARIANTS 泄漏 0
                                              （被否决过的字对不得被降级为拼写差异）
```

B 是**全量普查而非抽样**，因为这一侧一旦漏，丢掉的是校勘证据且计数型检查看不见——
与 `有能乾○九乾` 同一类失效（§2 / L-02）。八道闸门零回退，G5 由 PART → PASS。

## D-022 一处"两个数对不上"查出了 10 卷经文被错挂到别卷地址上

起因不是报错，是 `probes/probe_bcv.py` 在**同一次运行**里为 bible-web 打印了两个数：

```
len(vs)            31,102     parse_verses 返回的行数
len(parsed[slug])  29,214     这些行放进 {(卷,章,節): 文本} 之后的键数
```

差 1,888。这两个数被并列印在同一份输出里很久，没人对上过。**对不上的数就是缺陷报告**。

### 根因

`book_in_line` 只认序数**单词**（`first|second|third|i{1,3}`），不认**阿拉伯数字**。
而 WEB 每一卷标题都写作 `Book 12 2 Kings`。于是 `2 Kings` 匹配裸名 `kings`、
找不到序数词、落到 `want = b[0]` 得出 `1 Kings`——LIS 链上已有的名字，被当作重复丢弃，
**`2 Kings` 从此没有 span**。1/2/3 John 经由无序数的 `John` 同样丢失。共 **10 卷**。

### 后果：不是覆盖率问题，是静默返回别卷的经文

缺失卷的经文落进**前一卷**的 span，地址随之算错。而 `probe_bcv` 用字典推导建
`{(b,c,v): t}`，**后写者胜**，所以真正的经文不是被"重复"，是被**替换**：

```
Ruth 1:1  ->  'Now there was a certain man of Ramathaim Zophim ... Elkanah'   （这是 1 Samuel 1:1）
1 Kings   589 个冲突地址 · 1 Samuel 576 · Romans 358 · Ruth 85（Ruth 全书正好 85 節，即整卷被覆盖）
1,865 个冲突地址，持有不同文本的比例 100%
```

**而 5/5 控制用例全程通过**：它们测的 Genesis / Psalms / Isaiah / John / Revelation
恰好都是 span 正确的卷。这与 X-07 的 `有能乾○九乾` 是同一类失效——
**计数全绿、控制全过、文本是错的**（§2 / L-02）。

### 修正与刻意的保守

数字序数只在**紧贴卷名之前**才采纳：`(?:^|\s)([123])\s+$`，且它**优先于**行内别处的序数词
（数字紧贴它所修饰的名字，单词可能属于别的东西）。**刻意不放宽**为「名字前的任意数字」：
`Book 21 Ecclesiastes` 会取到 "21" 里的 "1"、去找不存在的 `1 Ecclesiastes`，
反而把这个标题丢掉——放宽一处会打坏另一处。

修正后：**66/66 卷，31,102 行，零地址冲突**，KJV 侧 24,995 不变，八道闸门零回退。

### 顺带修掉的两个"闸门不是闸门"

1. `probe_bcv.py` 是八道红线之一，却**永远 exit 0**——包括打印「56/66 卷」那一次。已加 `sys.exit(1)`。
2. 新增两条对照：**任何地址不得持有两段不同文本**（`rows == distinct keys`）、
   两部全本圣经必须都到 66 卷。前者是通用判据：一个地址映射到两段不同文本，
   意味着两处原文在争同一个引用，**这在引用系统里永远是缺陷**，与语料无关。

## D-023 三类知识用**两个文件**隔离；证据用持久引用；「认输」必须存得下

G8 判据是 Source / Derived / Conversation 在**存储与输出中物理隔离**。此前只有 Source，
所以隔离是**空真**。补它时有三个决定，每个都有实测依据。

### 一、两个文件，不是两个标志位

| 方案 | 结论 | 依据 |
|---|---|---|
| A `unit` 加一列 `provenance='source\|derived'` | **否决** | 依赖每个查询都记得加过滤。D-008 已有先例：經/注 曾共用一个 layer 值，`merge_units` 就把它们融成一块。**依赖"记得过滤"的区分最终一定会漏** |
| B 同一 db 内新增表 | **否决** | `ingest.build()` 第一行是 `os.remove(db_path)`。corpus.db 每次构建都删掉重建，而本项目**刻意**把这当 5 秒的日常操作。**Source 可从 `data/raw/` 再生，Derived/Conversation 不能**——一次例行重建就静默毁掉全部推导结论 |
| C 独立文件 `knowledge.db` | **采纳** | 隔离能用**文件边界**陈述：corpus.db 里根本没有那些行，不存在忘记过滤这回事。且两者生命周期彻底分开 |

### 二、证据不能用 `unit(id)` 引用

unit id 来自构建期计数器（`uid += 1`），**跨重建不稳定**。一条引用 `unit 1234` 的结论，
下次构建后会指向**另一段原文**——而它看起来完全正常。因此证据存**持久引用**：
`work_id / file / raw_start / raw_end / page_anchor / scheme / addr1 / addr2 / quote`，
正是 D-005 认定的"一段原文的身份"。附带收益：`knowledge.verify()` 能把每条引文
**回查 `data/raw/`**，corpus.db 整个删掉也不影响可审计性。

### 三、`NOT NULL evidence` 会让 G7 存不进去——这是提前避开的 D-015

最自然的写法是给 `derived` 加一个 `NOT NULL` 的证据外键，强制"任何结论必须有证据"。
**那会让「证据不足」这类输出根本无法存储**，而那正是 G7 的要求。
这与「把卦/爻写成列名」（D-015）是同一类错误：**把当前用例的假设焊进 schema**。
区别是这次在犯之前拦住了。做法：`kind='refusal'` 免除证据要求，其余四类
（summary/diff/link/answer）在 API 层无证据即 `ValueError`。

### 四、闸门是**证伪式**的，照 U-01 的先例

`probes/probe_g8_isolation.py` 不断言隔离成立，而是**尝试 9 项越界**并报告是否被拦：
源检索 API 能否取到推导文本、corpus.db 里有无推导文本/表、无证据断言能否入库、
认输能否入库（**反向义务**）、重建是否毁掉推导知识、结论能否回溯到原文、
证据是否用了不稳定的 row id、有无孤儿断言。**9/9 全部被拦**。

这个闸门当场抓到我自己的一个缺陷：`verify()` 初版只 fold + 去空白**没去标点**，
于是 KR1a0001 的 `初九、潛龍勿用。` 报陈旧、KR1a0006 的 `初九濳龍勿用` 通过——
与 citation 0/30 那次**完全相同的 signature**（L-18）。

## D-024 G7 的回答层**不生成文字**；判据必须两半同时考

G7 判据：「无证据时明确输出『证据不足』，不编造。对抗性测试通过率 ≥ 95%」。

**关键设计：`guji.answer` 不做任何转述。** 每个"答案"都是一组检索到的原文，
各自带 file 与 page anchor。一旦回答层开始转述，它的输出就**不再可回查 `data/raw/`**，
而本项目实测最严重的失效正是"看起来像原文但不是原文"（X-07 的 `有能乾○九乾`）。
所以 `Answer.evidence` 装的是引文，`Answer.refused` 装拒答理由。

**两半必须同时考，只考一半毫无意义**：全部拒答则第一半 100%，全部作答则第二半 100%。

```
must_refuse  伪造/不存在的文本 → 必须输出证据不足    30/30 = 100%
must_answer  真实存在的文本   → 必须给出证据、不得拒答  25/25 = 100%
impossible   不可能的地址（卦65、乾卦六二）→ 必须拒答   4/4 = 100%
damaged 规则 仅命中损坏区 → 拒答；同址正确读法 → 仍作答  PASS
FABRICATIONS 0（不设容差）
```

对抗样例复用 G1 题库的 30 条**相邻换位**变体——**字符多重集与真文完全相同**，
所以任何"看起来像乱码就拒答"的启发式都过不了。

**`damaged` 规则是这一条不等于 `if not hits: refuse()` 的原因**：
命中集**全部**落在质量闸门标记区时必须拒答，尽管 hits 非空——
KR1a0006 卦61 印的是 `翰青登于天`，而见证本作 `翰音登于天`。
把 OCR 损坏当证据返回，是"平静地返回原文里不存在的文字"的另一种形式。
反向义务同时断言：**正确读法 `翰音登于天` 必须仍能作答**（返回 5 条）。

## D-026 通用性的证据是四种体系**形状不同**，不是数量到了四

`booksec`（第四种）落地后，很容易把「支持 4 种地址体系」当成通用性的证据。**它不是。**
四个解析器套在四本书上、底下却是同一种形状，只能证明代码被抄了四遍。
所以判据换成：**四种体系分别把列模型压在不同的地方**（`probes/probe_four_schemes.py`）。

| 体系 | addr_name | addr1 | addr2 | 它压的是哪一处 |
|---|---|---|---|---|
| `zhouyi` | 卦名 | 卦號 1..64 | 爻位**标签** | `addr2` **不能**是 INTEGER：用九/用六 是真实可编址单元且无序数位置 |
| `bcv` | 卷名 | 章 | 節（序数） | **三级**塞进两列 + 一个名字；且唯一 `addr_name` 空间开放（66 卷）而非固定 64 |
| `yilin` | 本卦 | 本卦號 | 之卦名 | `addr1`/`addr2` 是**同一类实体的两个位置**，不是「容器+位置」。矩阵，不是层级 |
| `booksec` | BOOK | 卷 | 节 | **同一体系两种深度**：Herodotus 用 763 节，Darwin 的 `addr2` 全为 NULL（只有 14 章） |

四种形状互不相似，`(scheme, addr_name, addr1, addr2)` **一列未改**。这才是 D-016 的回报。

`yilin` 那一行值得单独看：它**也是关于卦的**，却在旧的 `gua`/`yao` 列式 schema 下
**装不进去**——因为它需要的是「卦 × 卦」，不是「卦 + 爻」。同一个领域里都能出现装不下的形状，
说明 D-015 那次证伪的教训比"换一部书"更普适。

### 顺带查出一个 join key 缺陷

这张表第一次跑出来时，`yilin` 有 **65** 个 `addr_name` 却只有 **64** 个 `addr1`。
多出来的那个是 卦29：条目层记 `坎`（本书写法），标题层记 `習坎`（底本正名）。
**地址是跨作品的 join key**——若 焦氏易林 存 `坎` 而周易诸本存 `習坎`，
按名字连接两部书会**静默返回空**。已改为一律用底本正名；本书自己的写法仍在单元文本里，
**版本的正字法属于文本，不属于 join key**。

### Herodotus 推翻了台账对它的描述

台账原记 Herodotus「只有页锚点，无正典地址」。**恰好相反**：它有 763 个正典节、
**零个页锚点**；而 Darwin 有 **491 个页锚点**、无比章更细的地址。
两者合起来才是 `schema.sql` 开头那句（D-005「两者都需要且不可互换」）的**双向检验**，
单独任一本书都证不出来。这也再次说明「未编址」不等于「无结构」（L-16）。

## D-027 `text-damage` 必须要求 OCR 签名；并补一个**已知阴性**对照

D-020 修好地址窗口后，KR1a0006 **卦47上六** 由 `span-overextended-A` 改判为 `text-damage`
（contiguity 0.199），并被记为待办 P-01。并排读原文后（`probes/probe_gua47.py`）结论是
**它没有损坏，是判据的假阳性**：

```
卦47上六   形近替换 2 处（纏/纒 正字法、困/因），最长公共段 92 字
           KR1a0006 的段落只是越界续进了 卦48 井；KR1a0007 另有 音義/疏
卦61上九   形近替换 19 处（青/音 狀/飛 堵/者 寳/實 届/居 芝/之 絃/終 筆/華…），最长公共段 6 字
```

**改法**：`text-damage` 除 contiguity < 0.25 外，还要求 `substitutions >= 5`——
即「同一段文字里散布大量形近小替换」这个**机制签名**。**长公共段是反证。**
卦61 对照仍触发，卦47 释放。

### 为什么这不是"多标一个更安全"

这条是本项目对"保守"的一次修正。在引用系统里两个方向**对称**：

* 漏标 → 把损坏文本当证据交出去；
* **假阳性 → 拒绝交出真实证据**（卦47 进了 `suspect`，G7 的 damaged 规则就拒答它），
  而且**除非有人真去读那段原文，否则完全看不见**。

所以 L-03「没有已知阳性对照的闸门等于没有闸门」需要补一句：
**只有阳性对照的闸门会向"全标记"漂移**。`check_quality.py` 因此新增
**已知阴性对照**：卦47上六 必须**不**被判 `text-damage`，失效即 exit 1。

### 一条一般化的观察

这个缺陷是**修好上一个缺陷之后才长出来的**：窗口口径变准 → contiguity 数值变化 →
判据误判。**改动的下游要重新逐条看，而不是只看闸门有没有变红**——
本轮八道闸门在卦47 被误判期间**全部是绿的**。

## D-028 U-06 Douay-Rheims 接入：单独解析路径 + at_address scheme 过滤（本窗口）

**起因**：任务书把 U-06 列为下一窗口首要任务，并附勘查结论"bcv.VERSE_RE 应能匹配 Douay"、"75 个不同书名"。照 GOAL §2 纪律先实测复验。

**实测推翻的两个勘查结论**：

1. `bcv.VERSE_RE = ^\s{0,6}(\d{1,3}):(\d{1,3})\s+(\S.*)$` 在 group2 后要求 `\s+`，但 Douay 是 `1:1.`（点紧跟，非空白），`VERSE_RE.match('1:1. In the beginning')` 返回 None，`bcv.parse_verses` 对 Douay 返回 0 节。勘查结论"应能匹配 Douay"**被实测推翻**。
2. `^(\S.+) Chapter (\d+)\s*$` 全量匹配实测 **73 个** distinct 书名（1334 个章标题）。勘查结论"75 个不同书名"**被实测推翻**。

**决策：Douay 单独解析路径，不并入 bcv.parse_verses**

理由：三种圣经格式实测不同（KJV `1:1 In`、WEB `001:001 In`、Douay `1:1. In`），但 KJV/WEB 共享 bcv.VERSE_RE（`\s+` 匹配空格），Douay 不匹配。把 VERSE_RE 改成 `(\d{1,3}):(\d{1,3})[.\s]+` 能覆盖三种，但会引入歧义：KJV 的 `1:1 In` 与 Douay 的 `1:1. In` 在同一正则下无区分，且 KJV/WEB 的经文号后必跟空格、Douay 必跟点号——这是译本的硬性格式约定，不应当成可选。**结论**：Douay 走独立模块 `src/guji/douay.py`，bcv.VERSE_RE 不改。

**实测的 Vulgate 编号特性（已显式记录于 probe_bcv.py，不静默放宽闸门）**：

- Psalms 113：Vulgate 把 Protestant 诗篇 114+115 合并为一章，章内经文号 1-8 重置一次（8 个同-(C:V) 重复）。
- Proverbs 12:12：同一节号 12:12 印两次，文本不同（1 个同-(C:V) 重复）。

**接入过程发现的真实缺陷（已修复）**：

## D-047 term_time 节气求解绕行缺陷修复 + web 边界输入验证 + liuyao time 解包（2026-08-16）

### 起源

### 缺陷 1：term_time 节气求解绕行（红线级，影响八字大运+黄历月支）

**根因**（亲自跑诊断脚本定位，非猜测）：`gap()` 用 `v if v > -180 else v+360` 处理
0°/360° 绕行，但归一化只在 `v > -180` 时生效。太阳黄经接近 360° 时 `gap` 从 +305°
跳到 -43°（虚假符号变化，score=|prev_g|+|cur_g|≈356）。兜底扫描 `step=8` 命中这个
3 月底的虚假穿越点，二分求解返回春分时刻而非立夏/芒种/小暑/立秋等。

**影响范围**（2020-2026 多年份核实，全错）：立夏/芒种/小暑/立秋/白露/寒露/立冬/大雪
全返回春分或小寒时刻；八字大运起运岁数（依赖节气交界）+黄历建除/神煞（依赖月支）+
夏季之后所有日期的月支计算错误。

**修复**（commit f81f18d）：
1. `gap()` 改用最短角距离 `(v+180)%360-180`，让 360°/0° 边界连续，绕行不再产生
   虚假符号跳变
2. 兜底扫描记录**所有**符号变化点，按 `score=|prev_g|+|cur_g|` 选最小——真穿越点
   `gap` 过 0°（score≈4），绕行跳变在 ±180° 附近（score≈356）
3. 找到真穿越点后再进二分求解

**验证**：2026 全 12 节气 CST+8 对照 USNO 全对；2020/2023/2024/2025 多年份抽查
（立夏/冬至/立秋/春分/夏至/霜降）全对；13 闸门无回退。

### 缺陷 2：liuyao time 正常输入报 400（边界探活意外触发的既有 bug）

**根因**：`lunar.solar_to_lunar` 返回 `dict`（键 year/month/day/is_leap/month_cn/
day_cn/ganzhi_year/ganzhi_year_cn），而 `web/app.py` 原用 `ly, lm, ld, _ =
solar_to_lunar(...)` 解包，必然报 "too many values to unpack (expected 4, got 8)"。
正常 time 起卦返 400，用户无法用。

**修复**（commit 5369b8f）：改 `lm_info = solar_to_lunar(...); ly,lm,ld =
lm_info["year"/"month"/"day"]`；`cast_time` 第一参数原误传公历 `req.year` 改为
农历年 `ly`。验证：liuyao time 正常输入返 200。

### 缺陷 3：web 边界输入验证缺失（红线⑤「边界输入是否报错」）

**问题**：`/api/huangli` 缺 month/day 校验（y=1899/m=13/d=32/m=0 全返 200）；
`/api/liuyao` time 缺 year/month/day/hour 范围校验（越界返 200）。

**修复**（commit 5369b8f）：huangli 补 month(1-12)/day(1-31) 校验+datetime 越界兜
400；liuyao time 补 year(1900-2100)/month(1-12)/day(1-31)/hour(0-23) 校验。验证：

### 决策依据
- **修复而非绕行**：`term_time` 缺陷是红线级（影响八字+黄历两个核心面），不能像神煞层
  那样"避开"，必须根治。修复后神煞层探针不再受限月份。
- **gap 用最短角距离**：比原 `v if v > -180 else v+360` 更稳健，360°/0° 边界连续，
  无虚假跳变。兜底扫描按 score 选最小是关键——真穿越与绕行跳变混在一起，但 score
  差 90 倍，可可靠区分。
- **边界验证在端点层**：而非在 `huangli_mod`/`liuyao_mod` 计算层，因为计算层函数
  本身对越界输入会抛 ValueError（已是合理行为），端点层只需把它转成 400 中文报错。
- **不修复不影响主线的项**：`wuxing-dayi` 仅 1 单元入库失败、`bible-kjv/web/
  darwin-origin` 在 work 表但 0 单元——这些是"P2 语料扩充"的遗留，不影响核心检索面，
