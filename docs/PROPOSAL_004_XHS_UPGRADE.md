# 方案提案 004：让结果「看得懂、想分享」——面向小红书用户的内容温度升级

**Created**: 2026-08-20（优化轨，基于用户指示 + 搜索大模型调研）
**Status**: Proposal（待用户拍板 P4；P2/P3 待审查轨收编为 `specs/004` 或用户授权直做）
**上游输入**: 用户提供的搜索大模型调研（小红书 18–30 岁女性用户画像 + 10 个开源项目）
**与 spec 003 的关系**: 003 管「视觉壳」（点击目标/对比度/动效/回滚），
本方案管「内容芯」——同样一句话，用什么口吻、什么结构、什么形态交付。
两者都动结果区 UI，**必须同批排期**（见 §6）。

---

## 0. 一句话结论

**问题不是「没有 AI」，是解读层的口吻是审计报告，不是人话。**
温度来自文案，不来自模型：把写死的模板从「坐标转述体」改写成「闺蜜口吻」，
配上确定性推导的幸运色/数字（河图数 + 五行配色，本身就有古籍出处），
再加可分享的结果卡片——全部在宪法红线内（确定性、引文分离、闸门全绿），
**不需要重新引入 LLM**。

---

## 1. 诊断：为什么现在的结果「看不懂也不想看」（附实测证据）

真实输出（复验命令在文末 §7，1998-07-20 14 时女命问「感情运怎么样？」）：

> ## 排盘坐标
> - 四柱：戊寅年 己未月 戊辰日 己未时　日主：戊　大运：逆
> ## 十神格局
> - 年干戊 → 比肩：同类相助……（依据：戊戊同为土，同阴阳）
> - 月干己 → 劫财：……（依据：戊己同为土，异阴阳）
> …（共 8 行推导链）
> ## 针对「感情运怎么样？」
> - 夫妻星出现在：年支藏干甲(七杀)——夫妻星现于盘中，相关事项在四柱里有着落点
>
> 以上为系统按写死规则对运算坐标的转述，非生成文本、非现实决策依据……

五个具体断点（全部可指到行号）：

| # | 断点 | 证据 |
|---|---|---|
| 1 | **提问只得到一行坐标**，无情绪价值。「感情运怎么样」的答案里没有一个字回应情绪 | `interpreter.py:266-292` `_focus_lines` 只做关键词→坐标筛选 |
| 2 | **推导链直接暴露**。「依据：戊己同为土，异阴阳」是给校验者看的，不是给用户看的 | `interpreter.py:142-144` |
| 3 | **结论后置、术语前置**。首屏先见「排盘坐标/纳音」，用户 3 秒内看不到与自己有关的任何结论 | `interpret_bazi` 的 sections 顺序 |
| 4 | **防御性免责声明压轴**，以「非现实决策依据」的口吻收尾 | `interpreter.py:68-69` |
| 5 | **零可分享物、零轻量钩子**。没有幸运色/数字/卡片/海报；入口 8 个功能卡没有「今日运势」引流位 | `index.html:48-69`；仓库 293KB 动画素材未接线（spec 003 已证实） |

六爻更极端：用户问感情，得到的回答是
「系统只给卦象坐标与經文原文，不代为断事——请据下方卦爻辞原文对照所问（G7）」
（`interpreter.py:376-378`）。**这是把 G7（无证据不推测）误用到了拒绝服务的程度。**

G7 防的是**伪造古籍引文**，不禁止温柔地说话。

## 3. 核心设计：双层口吻 + 四层内容 + 可回滚

### 3.1 「闺蜜模式 / 专业模式」双模式（本方案最重要的一条机制）

- **闺蜜模式（默认）**：温柔短句、第二人称、emoji、幸运色数字卡片。
- **专业模式**：**逐字节等于现在的输出**，一键切换，localStorage 记忆选择。
- 与 spec 003 US5（视觉一键回滚）同构：**口吻方向选错可零成本切回**，
  这也是「优化轨自主决定文案风格」能成立的前提。两套模式共用同一个切换器。

### 3.2 四层内容结构（闺蜜模式下的结果区）

以「感情运怎么样？」为例（同一输入，闺蜜模式目标输出）：

> **✨ 一句话**（L0，≤20 字）
> 土土相叠的安稳盘，感情是慢热但耐放型。
>
> **🌿 你的能量卡**（L1，卡片，可分享）
> 本命元素：土 🟤（像大地，稳、恋家、认准不放）
> 今日幸运色：象牙白 ⚪ · 幸运数字：5、0（河图土数）· 幸运时段：19:00–21:00
> 今日关键词：安稳 · 表达
>
> **💌 给你的一句话**（L1.5，回应提问的情绪层）
> 问感情——你的盘里夫妻星在年支，属于「先做朋友、慢慢升温」的路线；
> 今天流时正官透出，适合认真聊一次，不适合下结论。
>
> **📖 想看依据？**（L2，默认折叠）→ 现有 sections 改写版
> **📜 古籍原文**（L3，默认折叠）→ 现有 citations **原样保留**

红线不变的部分：L1.5 只做「描述 + 开放式提示」，不做吉凶断言与现实指令
（不说「你会脱单」，说「属于慢热路线」）；L3 引文与出处逐字节不动。

### 3.3 幸运色/数字不是编的——河图数与五行配色本身有古籍出处

- 数字：河图「天一生水地六成之……天五生土地十成之」→ 水一六、火二七、
  木三八、金四九、土五十。取用户日主五行 + 当日五行生克确定。
- 颜色：五行配色通行对应（水黑蓝、火红紫、木青绿、金白金、土黄棕）。
- **这是本方案最划算的一处**：小红书用户最爱的「幸运色/幸运数字」，
  在本项目里反而是**可引用的古籍知识**（可挂《系辞》引文），
  与开源竞品们拍脑袋的随机数形成本质差异——「有出处的玄学」正是本项目的立身之本。

## 4. 分期方案

### P0 解读文案层重写（最先做——后面所有功能都要往这个口吻里装）

| 项 | 内容 |
|---|---|
| 做什么 | `interpreter.py` 每个返回体增加 `warm` 视图（L0/L1/L1.5 文案 + 幸运推导），**计算层、citations、专业模式输出零改动**；前端 `renderInterpretation` 支持双模式切换 |
| 不做什么 | 不改 `src/guji` 计算模块与 `data/`；不做吉凶断言/医疗投资法律建议；warm 文案不进 corpus.db / knowledge.db（与现 text 同等待遇，只落 history.db） |
| 宪法兼容 | 同输入必同输出（纯函数模板）；引文分离不动；「仅供娱乐」进免责声明 |
| 验收 | selftest 新增断言：warm 视图存在且确定性（两次运行逐字节相等）、L0 非空 ≤20 字、幸运色/数字与河图映射一致、免责声明含「仅供娱乐」；探针：闺蜜模式首屏（L0+L1）术语命中数 ≤3（术语表写死在探针里） |

### P1 结果卡片 + 分享海报（视觉化 + 社交化）

| 项 | 内容 |
|---|---|
| 做什么 | L1 能量卡组件化（色块、关键词、牌面）；塔罗牌面用 **CSS 绘制**（78 张=名称+编号+分类配色，零图片资源）；抽牌翻牌 CSS 3D 动画（接线仓库内 animotion 素材，正好清 spec 003 指出的 293KB 债）；**分享海报**：vendor `html2canvas` 单文件（MIT，~48KB），生成 3:4 竖版海报（能量卡+日期+站名+「仅供娱乐」水印），直接保存/分享 |
| 不做什么 | 不引 CDN（运行时零联网）；不引构建工具链（保持 vanilla JS 单文件架构）；不引 react-three-fiber（用 CSS transform 实现 anois/tarot 的 3D 效果） |
| 宪法兼容 | 新依赖按宪法 §5 记 provenance（sha256 / source_url / licence / fetched_at 入 `vendor/README`）；海报属生成内容，只在前端产出，不落库 |
| 验收 | 探针：海报 `toDataURL()` 长度 > 阈值；`index.html` 与 app.js 零外链资源（静态检查）；UI smoke 扩展「分享按钮点击后出图」用例；reduced-motion 下翻牌动画归零 |

### P2 今日运势首页 + 星座日运（引流入口）⚠ 新增品类

| 项 | 内容 |
|---|---|
| 做什么 | 入口第一位改为「今日运势」聚合卡：黄历宜忌（`huangli.py` 数据已有：建除/二十八宿/彭祖百忌，改写口吻）+ 本命日运一句话（P0 复用）+ 幸运色/数字/时段；**星座日运**：12 星座 × 当日干支五行规则推导（星座元素 × 日五行生克 → 写死的文案块），无随机数、同日同座必同输出 |
| 不做什么 | 星座内容与古籍引文**物理分开**：独立 API 路由、UI 分区、独立免责声明「西方占星为娱乐模块，非本项目古籍语料」——不混排，不进 corpus |
| 治理 | spec 003 Out of Scope 明说「新增算命品类另立 spec」→ 本节即 `specs/004` 底稿，待审查轨收编或用户授权直做 |
| 验收 | 确定性断言（12 星座 × 同一天全量输出逐字节可复现）；UI smoke；星座文案块与 corpus 探针（`probe_no_generated_in_corpus` 扩展覆盖） |

### P3 MBTI × 塔罗混搭（社交标签，最强分享物）⚠ 新增品类

| 项 | 内容 |
|---|---|
| 做什么 | 24 题二选一问卷 → 16 型；每型写死映射一张塔罗大阿卡纳「本命牌」+ 五行气质描述（例：INFJ·隐士·水木）；结果页 = 能量卡 + 本命牌 + 一段自我探索文案 → P1 海报一键分享 |
| 借鉴 | `adds9810/your-tarot-mbti` 的产品形态（它用 Gemini，我们用写死映射——16×1 映射表不需要模型） |
| 验收 | 16 型全覆盖断言；映射表双向一致；题目计分纯函数自测 |

### P4 决策点：BYOK AI 深度解读（**需要用户拍板，不默认做**）

- **宪法冲突**：R178b 刻意移除 LLM（成本/网络/不可复现），spec 003 Out of Scope
  明确排除「重新引入生成式模型解读」。
- **若用户要**：仅 BYOK——用户自己的 API key 存 localStorage，服务端零 key 零成本；
  输出永远标注「AI 娱乐解读」，与引文系统物理隔离，不落任何 db，不参与检索。
  相当于「用户自带模型的 optional 前端插件」，服务端架构不受影响。
- **建议**：先不做。P0–P3 解决 95% 的「看不懂/不想看」；P4 等 P0 上线后看留存再议。

## 8. 明确不做（Out of Scope）

- 不重新引入默认 LLM（P4 仅 BYOK 且待拍板）。
- 不把星座/MBTI/塔罗文案与古籍引文混排或入库（生成内容隔离红线）。
- 不引入前端构建工具链/npm 依赖树（保持单文件 vanilla JS + vendor 单文件）。
- 不动 `src/guji` 计算层语义与 `data/` 语料。
- 不做小程序/App 形态（远期另议）。
