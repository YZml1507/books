## 1. 系统目标：什么叫「AI 真正读过一本书」

拒绝模糊表述。下列九条是**可验证判据**，每条给出通过条件与当前状态。

| # | 判据 | 通过条件 | 当前 |
|---|---|---|---|
| G1 | 能找到原文 | 给定概念，返回的原文片段人工核验准确率 ≥ 95% | 未测 |
| G2 | 能精确定位 | 每个片段可回溯到 书→版本→卷/篇→单元→原文，且**锚点在原始文件中可字符串匹配** | 部分（Kanripo 有 1,077 页锚点） |
| G3 | 能区分版本 | 同一著作的两个版本被识别为"同作品、异文本"，差异可枚举 | 素材就绪（原本/別本周易本義） |
| G4 | 能跨单元关联 | 多跳检索：由 A 单元发现的实体触发 B 单元检索，链路可展示 | 未实现 |
| G5 | 能比较注家 | 给定同一爻位，并列输出王弼/程頤/朱熹三家原文 + 差异摘要 | **被 D-006 阻塞** |
| G6 | 能引用证据 | 每个结论附可核验引用；引用错误率 ≤ 1% | 未测 |
| G7 | 能承认证据不足 | 无证据时明确输出"证据不足"，不编造。对抗性测试通过率 ≥ 95% | 未实现 |
| G8 | 能区分知识来源 | Source / Derived / Conversation 三类在存储与输出中物理隔离 | 未实现 |
| G9 | 能长期研究 | 跨会话恢复：哪本书、哪版本、哪些原文、何结论、何证据 | 未实现 |

**G2 的严格定义**：引用锚点必须能在原始文件里字符串匹配到。这条排除了"AI 生成的

## 2. 总体架构

不照抄线性流水线。真实数据决定了三处必须偏离常规设计：

```
                    ┌─────────────────────────────────────────┐
   Source Adapter   │ Kanripo · Gutenberg · Local · daizhige   │
   (可替换)         └────────────────┬────────────────────────┘
                                     │ + provenance(sha256/url/time/licence)
                    ┌────────────────▼────────────────────────┐
   Parse Layer      │  双引擎并行解析 → 分歧检测 → 质量闸门    │  ★偏离1
                    │  PyMuPDF(主/页码) ∥ markitdown(校验/表)  │
                    │  分歧或坏码位 → 隔离 → OCR 路径          │
                    └────────────────┬────────────────────────┘
                    ┌────────────────▼────────────────────────┐
   Normalise        │  異體字折叠 · 无码位字形占位 · 逐字切分  │  ★偏离2
                    └────────────────┬────────────────────────┘
                    ┌────────────────▼────────────────────────┐
   Structure        │  单元切分 + 双地址：                     │  ★偏离3
                    │   ① 引用地址(page anchor, 版本局部)      │
                    │   ② 对齐地址(canonical ref, 跨版本)      │
                    │   对齐不上 → unknown，不猜               │
                    └────────────────┬────────────────────────┘
                    ┌────────────────▼────────────────────────┐
   Index            │  FTS5(逐字切分) + 向量(可选) + 元数据     │
                    └────────────────┬────────────────────────┘
                    ┌────────────────▼────────────────────────┐
   Agent            │  检索即推理：判型→选书→选章→读→扩展→验证 │
                    └────────────────┬────────────────────────┘
                    ┌────────────────▼────────────────────────┐
   Output           │  答案 + 引用 + 证据充分性判定             │
                    └─────────────────────────────────────────┘
```

**偏离 1 — 解析层是双引擎而非单引擎。**
因为实测发现两个引擎的失败方式相反：PyMuPDF 静默产出貌似合理的错字，markitdown
显式输出 `(cid:N)` 占位。二者分歧处即不可信字符。这让质量闸门几乎免费，
比"选一个最好的解析器"更可靠。详见 D-001。

**偏离 2 — 归一化是独立的一层，不是解析的附属步骤。**
因为異體字问题有两种独立形态：单书内混用（傳/𫝊 漏 45%），和跨来源系统性相反
（Kanripo 无 / Gutenberg 無，同一句命中 1 vs 0）。且 NFKC 完全无效。折叠必须在
索引与查询两端同时施加，因此它必须是可独立测试的一层。详见 D-003。

**偏离 3 — 每个单元携带两个地址，而非一个 ID。**
因为页锚点是版本局部的（三本子 BASEEDITION 与卷号体系互不兼容，同一段话出现次数
都不同），不能用来对齐；而对齐地址（卦+爻位）不能用来引用（它不指向具体印本位置）。
两者职能不同，必须并存。详见 D-005。

## 3. 书籍解析层

### 3.1 分流

按**实测特征**分流，不按文件扩展名：

```
每页字符数 < ~50                      → 扫描件，走 OCR
(PUA + CJK-Ext-A) 占比 > ~0.5%        → 坏 CID 字体，隔离
markitdown 含 (cid:N) 而 PyMuPDF 有字 → 该字符不可信，隔离
两引擎均 0 字符                       → 纯图像，走 OCR
以上皆否                              → 文本层可信，进入归一化
```

`(cid:N)` 是 ASCII，纯码位普查会漏掉，必须显式统计——这是我自己踩过的坑。

### 3.2 各格式的保留目标

| 格式 | 必须保留 | 实测约束 |
|---|---|---|
| Kanripo txt | `<pb:>` 页锚点、`¶` 短语界、`(...)` 注文、`○` 疏节、卷属性 | 注文中位数长度 17 字（王弼注）/ 43 字（注疏） |
| PDF | 页、标题、段、脚注、表、阅读顺序 | 表格扁平化会打乱阅读顺序；`get_label()` 常为空 |
| EPUB | book/chapter/section/paragraph/metadata | markitdown 只恢复 2 个标题且均为样板 → 需 EbookLib 走 spine |
| 扫描古籍 | 页图、OCR 置信度、图文对应 | PyMuPDF `get_pixmap` 可用，150 dpi 约 6 MB/页 |

### 3.3 古籍专项

竖排、繁体、異體、无标点、注疏混排是**同时**出现的，不能分开处理。
经/传/注/疏必须区分为不同 `layer`，因为"比较注家"要求按 layer 过滤检索。
Kanripo 的 `(...)` 与 `○` 提供了机器可读的 layer 线索，这是选它作基座的另一个理由。

## 4. 书籍知识模型

只保留有实测需求支撑的实体，不为复杂而复杂。

```
Work            抽象著作（"周易"这一著作本身）
 └─ Edition     具体文本（KR1a0001/tls、KR1a0031、Gutenberg#25501）
     └─ Unit    最小可引用单元
         ├─ citation_addr   页锚点等，版本局部，用于引用
         ├─ canonical_addr  卦+爻位等，跨版本，用于对齐；可为 unknown
         ├─ layer           經/傳/注/疏/正文
         └─ attribution     注家/译者/编者
Agent-side:
Concept · Entity · Claim · Interpretation · Evidence
```

**为什么 Work 与 Edition 必须分开**：实测证明"同一部书"不是单一文本——
原本/別本周易本義 是同著作的两版；Kanripo 与 Gutenberg 的《易经》体量差 1.72 倍
且用字约定相反。若合并为一个实体，这些差异会被静默抹除。

**为什么 `canonical_addr` 允许 unknown**：因为 D-006 未解决。宁可标注"不知道"，
也不要写入 84% 覆盖率里那些漂移 610 单元的错误归属。**Unknown 是一等公民。**

**Claim / Interpretation 必须区分**：`Claim` 是原文说了什么（可引用），
`Interpretation` 是注家或 AI 的解读（需标注主体）。混同二者会让"比较注家"失去意义。

## 5. 多版本 / 多解释体系

对齐键是**作品内在地址**，不是页码。

```
Work: 周易
 ├─ Edition KR1a0001  正文        canonical: 卦+爻位  (64 卦标题可用)
 ├─ Edition KR1a0006  王弼注      canonical: 待还原   ← D-006
 ├─ Edition KR1a0007  王弼注+孔疏 canonical: 待还原   ← D-006
 ├─ Edition KR1a0016  伊川易傳(程頤)
 ├─ Edition KR1a0031  原本周易本義(朱熹)  ┐同一著作
 ├─ Edition KR1a0032  別本周易本義(朱熹)  ┘两个版本
 └─ Edition PG#25501  易經(独立数字化)   仅校验，零引用锚点
```

同一套模型迁移到《理想国》即：Work=理想国，Edition={希腊文, 英译A, 英译B, 中译A}，
canonical_addr = Stephanus 页码。迁移到《资本论》即 canonical_addr = 卷/篇/章节号。
**每部作品需要一套 canonical reference scheme**，这是可插拔的，不是硬编码。

跨来源校验已被证明有用：仅靠对比 Kanripo 与 Gutenberg 就发现了 無/无 约定相反，
以及 `自天祐之` 5 vs 4 的真实差异（原因待查）。差异本身就是折叠表的候选来源。
（补注 2026-08-15：原因已查清，见 DECISIONS.md D-034/T7-n——5 vs 4 指 KR1a0001(5) vs
KR1a0032(4)，是繫辭传在不同版本里的印次差异，源文真实差异，非抽取错误，不入折叠表。）

## 6. AI 阅读 Agent：检索即推理

拒绝 `问题 → 向量检索 → LLM → 答案`。

```
问题 → 判型 → 选书/版本 → 选单元 → 读原文
                                      ↓
                            发现新概念/实体 ← ─┐
                                      ↓        │ 多跳，有预算上限
                            扩展检索(可跨版本)─┘
                                      ↓
                            建立证据集 → 交叉验证
                                      ↓
                    证据充分? ──否──→ 明确输出"证据不足"
                        │是
                        ↓
                    答案 + 精确引用
```

**硬约束**：

- 不把整本书塞进 context。检索必须是推理的一部分，Agent 要能说明**为什么**检索到这些。
- 每个结论必须挂 `Evidence`，`Evidence` 必须挂可字符串匹配的 `citation_addr`。
- 遇到 `canonical_addr = unknown` 的单元，Agent 必须降级表述（"此段出处未定"），
  不得假装知道它属于哪一卦。
- 检索到的原文与模型自身知识必须物理隔离（G8），输出时可区分标注。

## 7. 研究模式

| 模式 | 用途 | 依赖 |
|---|---|---|
| Quick Answer | 单跳事实 | FTS5 + 折叠表 |
| Deep Research | 多轮检索阅读 | 多跳 + 证据集 |
| Chapter Study | 单章精读 | 单元切分 |
| Comparative Study | 比较注家/译本/版本 | **canonical_addr（被 D-006 阻塞）** |
| Cross-book Research | 跨书概念演变 | 概念层 |
| Concept Research | 单概念纵向追踪 | 概念层 |

`Comparative Study` 是用户最想要的能力（"比较王弼和朱熹对乾卦的理解"），
也是唯一被 P0 问题直接阻塞的模式。**它决定了实现顺序：先解决对齐，再谈其余。**

## 8. 长期记忆：三类知识物理隔离

```
Source Knowledge      来自原文，必须有 citation_addr，不可修改
Derived Knowledge     AI 从多来源推导，必须记录推导链与所用 Evidence
Conversation Memory   用户与 AI 的讨论过程
```

三者绝不可混同。「你还记得之前讨论的乾卦吗」应能恢复：书、版本、单元、原文、
当时结论、结论所依证据、以及哪些只是推测。

## 9. 数据来源与合规

Source Adapter 可替换，不绑定单一站点。每次获取必须记录
`sha256 / source_url / fetched_at / licence 状态`（已实现于 `corpus_manifest.json`）。

**已知合规缺口**：25 个 Kanripo 仓库无一含 LICENSE/COPYING。底本为前现代文献，
但数字化条款未声明 → 逐条记录实际状态，不假定宽松许可。daizhigev20 同样无 license
且无页码，仅可作语料。

访问事实（代理开启后）：`raw.githubusercontent.com`、`codeload.github.com` 均可用；
GitHub core API 配额耗尽（0/60）但 search API 可用，书目已缓存至 `data/catalog/`
以免重复消耗；`gutendex.com` 可用。

## 10. 实现顺序

顺序由风险决定，不由模块依赖决定。

1. **解决 D-006 卦对齐**（手工 gold set → 经文锚定 + 距离上限 + unknown → 打分）
2. **落地異體字折叠表**（用来源差异自动产候选）
3. **最小 ingest + FTS5 检索骨架**（修 `probe_pipeline.py` 路径并提升为正式模块）
4. **补非古籍测试书**，验证通用性
5. 双引擎质量闸门产品化
6. Agent 多跳与证据集
7. MCP / Skill（仅在成熟方案不够用时才自建）

**在第 1 步通过打分之前不建知识图谱。** 否则会把 84% 覆盖率中那些错误的卦归属
固化进实体关系，后期无法清除。GraphRAG / LightRAG 保持「未验证」状态。
