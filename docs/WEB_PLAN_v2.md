# 网页端 v2 重新设计方案（WEB_PLAN_v2）

> 状态：方案（2026-08-15）。针对用户实测反馈的两大问题重新设计：
> **① LLM 解读排版没做好（markdown 标记原样显示）；② 定位不对——只检索不运算，应该"排盘 + 运算 + 大白话回答"**。

## 1. 问题诊断（实测复现，非口头）

### 1.1 排版问题
- `web/static/index.html` 用 `esc()`（textContent 转义） + `.llm-text{white-space:pre-wrap}` 显示 LLM 输出。
- LLM（llm_reader SYSTEM_PROMPT）按 markdown 结构返回：`## 所依据的原文引文`、`**[1]**`、`- 列表`、`**结论**`。
- 结果：浏览器显示**原始 markdown 标记**（`##`、`**` 不渲染），可读性差。
- 根因：前端没有 markdown 渲染层；且 esc() 之后也无法安全渲染。

### 1.2 定位问题（核心）
- 现状：`POST /api/bazi` 返回 排盘 + 古籍引文 +（可选）LLM 解读。LLM 拿到的是**引文列表**，只做"资料呈现"。
- 用户要求：输入**生辰八字 + 当天日期时间地点**等全部必要元素，问"今天运气如何"，系统应：
  1. 排盘（已有）；
  2. **运算**——把 四柱/日主/纳音/大运 与 **当天干支/流日流时** 结合，算出十神关系、五行生克、地支冲合刑害等**结构化事实**（这是纯计算，不产生新文本，不撞红线）；
  3. 检索命理书原文作为**依据**（已有）；
  4. **用大白话回答"今天运势如何"**——把运算结果 + 引文依据融合成一段人话，而不是"算完丢给用户"。
- 红线不变：运算结果 = 结构化坐标事实（可核验）；LLM 回答 = 生成文本（标注、不落库）；引文仍单独列出。

## 2. 三层架构（在现有基础上加"运算层"，改"生成层"）

```
输入：出生 年月日时 + 性别 + 问事日期时间（+可选地点/问题）
  │
  ├─ ① 排盘层（已有 bazi.compute）
  │      四柱 / 日主 / 纳音 / 大运方向 / warn
  │
  ├─ ② 运算层（新增 src/guji/bazi_calc.py）——本次核心新增
  │      十神关系（日主 vs 四柱天干/藏干）
  │      五行统计（四柱五行分布、缺行）
  │      地支关系（六冲/六合/三合/相刑/相害，命局内 + 命局 vs 流日）
  │      流日/流时干支（问事日期时间 → 当日干支/时辰，与命局生克）
  │      → 输出结构化"运算事实"列表 [{fact, basis}]（basis=坐标，可核验）
  │
  ├─ ③ 检索层（已有 bazi_lookup FTS+bge）
  │      按日主/纳音/干支检索命理书原文 → 依据引文
  │
  └─ ④ 生成层（升级 llm_reader）
        新 prompt：排盘 + 运算事实 + 古籍引文 + 用户问题
        → 大白话回答（分条、先给结论再给依据、标注生成来源）
```

## 3. 运算层规格（src/guji/bazi_calc.py，纯标准库）

### 3.1 基础表（常量，照通行命理规则；写死、可核对）
- 天干五行：甲乙木、丙丁火、戊己土、庚辛金、壬癸水
- 地支五行+藏干：子(癸)、丑(己癸辛)、寅(甲丙戊)、卯(乙)、辰(戊乙癸)、巳(丙庚戊)、
  午(丁己)、未(己丁乙)、申(庚壬戊)、酉(辛)、戌(戊辛丁)、亥(壬甲)
- 十神：以日干为我 → 比肩/劫财/食神/伤官/偏财/正财/七杀/正官/偏印/正印
- 六冲：子午、丑未、寅申、卯酉、辰戌、巳亥
- 六合：子丑、寅亥、卯戌、辰酉、巳申、午未
- 三合：申子辰(水)、亥卯未(木)、寅午戌(火)、巳酉丑(金)
- 相刑：子卯、寅巳申、丑戌未、辰午酉亥自刑
- 相害：子未、丑午、寅巳、卯辰、申亥、酉戌

### 3.2 输出（运算事实，全部带坐标依据）
```json
{
  "ten_gods":      [{"label":"日主 庚 见 年干 甲 → 偏财", ...}],
  "five_elements": {"counts": {"金":3,"木":1,...}, "missing": ["火"], "strong": ["金"]},
  "relations":     [{"type":"六冲","a":"年支午","b":"日支子","note":"子午冲"}],
  "day_luck":      {"day_ganzhi":"甲子","day_master_rel":"甲为日主庚之偏财",
                    "day_branch_rel":"子与日支辰半合水局","hour_ganzhi":"..."},
  "summary":       "日主庚金生于亥月（休），五行缺火；今日甲子，甲为偏财，子与辰半合…"
}
```
`summary` 由运算层**拼接生成**（模板式，非 LLM），保证坐标正确；LLM 只负责把 summary+引文"说人话"。

### 3.3 问事时间的流日/流时
- 用 `bazi.day_ganzhi(问事日期)` 得当日干支（已实现、已验证）；
- 时辰用 `hour_ganzhi(日干, 问事时辰)`（已实现）；
- 与命局四柱逐一比对：冲/合/刑/害 + 天干十神关系。

## 4. 生成层（升级 llm_reader，新 SYSTEM_PROMPT）

输入组装（interpret 新签名）：
```
排盘：<render>
运算事实：<bazi_calc.summary + 关键 facts 列表>
古籍引文：<evidence 列表（带出处）>
用户问题：<今天运气如何？>（默认若空给"今天运势如何"）
```
SYSTEM_PROMPT 规则（更新）：
1. 先给**大白话结论**（1-3 句，直接回答用户问的"今天运势"），再分条给依据；
2. 依据只能来自"运算事实"和"古籍引文"，两者都没有的不得编造（G7）；
3. 运算事实是坐标，可说"按十神/冲合推算"；引文标注出处；
4. 输出用 markdown 结构（## / ** / - ），前端会渲染；
5. 结尾标注"以上为 LLM 生成解读，仅供参考"。

## 5. 前端改进（web/static/index.html v2）

### 5.1 markdown 渲染（选型见任务 2，两案）
- **案 A（推荐）本地迷你渲染器**：手写 ~80 行 `renderMD(text)`，支持 `## / ###`、`**加粗**`、`- 列表`、`> 引用`、`` `code` ``、`1. 有序列表`；先 esc() 再渲染，杜绝 XSS；零依赖、离线可用（打包单文件友好）。
- **案 B vendor marked.js**：把 marked.min.js 放入 `web/static/`（本地文件，不引 CDN），功能全（表格/链接）；多一个 ~30KB 文件。

### 5.2 新输入区
- 出生：年/月/日/时 + 性别（已有）
- **问事：日期 + 时间（默认今天）+ 地点（可选，仅提示用，不联网换算时区——本地按系统时区）**
- 问题框：默认"今天运势如何？"
- LLM 开关（已有）

### 5.3 结果区（四段）
1. 排盘卡片（已有，含 warn）
2. **运算结论卡片（新增）**：十神 / 五行缺行 / 冲合刑害 / 流日关系 / summary（结构化展示，非 LLM）
3. 古籍原文证据（已有，可展开）
4. **LLM 大白话回答（markdown 渲染 + 生成标注）**

## 6. API 契约变更（POST /api/bazi v2）

请求新增：`ask_date`(YYYY-MM-DD，默认今天), `ask_hour`(0-23，默认当前), `location`(可选)。
响应新增：
```json
"calc": { "ten_gods":[...], "five_elements":{...}, "relations":[...],
          "day_luck":{...}, "summary":"..." }
```
`llm.text` 改为大白话回答（markdown）。

## 7. 验证（先定后测）

1. **运算层单测**：已知八字手工核对——如 庚辰日主：甲=偏财、子午冲、五行缺火、今日甲子→偏财+子辰半合；逐条对照命理规则表。
2. **summary 正确性**：模板拼接，坐标字段与运算结果一致（脚本断言）。
3. **LLM 回答**：真实调用（已配 key），人工读：有结论、有依据、无编造、markdown 结构完整。
4. **前端**：浏览器实测 markdown 渲染（## / ** / - 正常显示）、运算卡片可见、四段齐全。
5. **13 道闸门零回退**；CLI（ask_bazi）同步扩展支持运算输出（--ask-date 等，可选）。

## 8. 红线遵守（不变）

- 运算层 = 纯坐标计算，不产生"新文本"（summary 是模板拼接，可核验）。
- LLM = 生成文本，标注、不落库、与引文分离（不变）。
- KEY 只留服务端（不变）。
- 新增依赖：无（运算层纯标准库；markdown 案 A 零依赖）。
