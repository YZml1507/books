# 周期四计划（2026-11-17 起）——从「字节优化」转向「布局 / 信息架构 / 功能决策」

## 背景与转向依据（用户质询 + 调研数据）

用户原话：「你好像一直在做删减代码，优化只能从这些地方去优化了吗？整个项目
就不能从排版布局（比如图片里面的左边太空）或者功能优化，项目的增删改去优化了
吗？」＋「是否需要加入一个登录系统用于存储和记忆用户的信息」。

调研结论（数据见 DECISIONS.md D-910~D-912）：
1. 前三周期（R1–R13）的削减类工作**有据可依**：首访实测 1,827.6KB / FCP 5.4s，
   性能是真痛点。该维度已基本收官（R13 关键 CSS 已验证等效）。
2. **布局存在实测缺陷**（不是口味问题）：
   - `styles.css:2706` `@media (orientation: landscape) and (min-width: 700px)`
     将 `.func-grid` 强制 2 列。该查询为横屏手机/平板设计，却命中**全部桌面
     宽度**：17 张功能卡排 9 行，1440 宽 docH 2058px（2.3 屏）、1920 宽两侧
     各空 410px。
   - hero 卡：熊居左、文案居右，中段空心；日卡为居中大竖卡；心情行
     `flex-basis:100%` 右对齐两颗按钮，中段空心（即用户截图所示）。
3. **登录系统不需要新建**：`web/userdb.py` + `routers/account.py` 已是完整
   轻账号体系（昵称+口令码、sha256(salt+passcode)、无状态不签 token、
   限速、乐观并发备份、Turso/本地双后端、备份负载服务端不解析），UI
   （#accountCard）已存在于排盘历史抽屉。实测生产跑**本地 sqlite**
   （未配 BOOKS_USERDB_URL），`data/users.db` 12 个账号全是 selftest 造的
   `st账号*`、records 全空——**真实用户 0**。问题在可发现性与持久化，不在缺失。
4. **功能增删缺数据**：全仓零埋点（无 analytics/telemetry）。无使用数据时
   砍/加功能皆为拍脑袋。
