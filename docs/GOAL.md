**硬约束：同一时刻只允许一个 agent 写共享状态。** 共享状态指：


理由不是洁癖，是本项目的真实事故：**同一张折叠表存在两份拷贝，对同样的字节给出了相反

**推荐工作方式**：子 agent 负责**只读的勘查与产出方案**（写自己的 `probes/probe_*.py`
和结论），把对 `src/` 与索引的修改**收回主线串行执行**，每次改完跑一遍 §3 全部闸门。

**注意最后两条**：它们发生在**我撰写这份警告文档的同时**。我一边写"不要相信口头结论"，
一边往同一份文档里塞了没测过的数字。这不是谦辞——它说明这类错误**不是偶发的疏忽，而是
默认行为**，必须靠"每条结论对应一条可执行命令"从流程上拦住，而不是靠小心。

**因此**：

- **文档里的数字一律当作"待复验"**，不是事实。事实只在脚本输出里。
- 任何一条结论，先跑对应命令确认，再往下走。跑不出来就当它是错的。
- 发现文档与实测不符时，**改文档并在文档里写明"此前结论已被推翻"**——本项目的做法是
  保留错误记录（见 `DECISIONS.md` D-008 那段被划掉的结论），不是悄悄改掉。
- **不要把"数字没变"当作"没有收益"，也不要把"数字变好"当作"改对了"**。两者都出现过反例。

**为什么这条如此重要**：本项目是一个**引用系统**。它最严重的失效不是崩溃，而是
**平静地返回一段原文里不存在的文字**。而这种缺陷**计数型检查完全看不见**——`有能乾○九乾`
在所有计数测试下都是通过的。所以"看起来对"永远不构成证据。

## 4b. 任务量与十小时连续工作

**任务量够，远超十小时。** T1 一项（评测集：四类题目、自动抽取、人工审核、
`scripts/eval_g1.py` + 题库）本身就是数小时量级；T7 有 18 个独立子项。

**但任务量不是连续工作的瓶颈，下面三件事才是**：

1. **T1 是设计密度最高的一项，而且排第一。** 它没有唯一正确答案，容易反复推翻。
   建议：先做**最小可运行版本**（每类 5 题，跑通 `eval_g1.py`，产出一个基线数字），
   立刻记入台账，**再迭代扩充**。不要追求一次做完美——本项目的教训是
   「先有可执行的复验命令，再谈质量」（`MASTER_PLAN.md` §8）。
2. **撞上 §1 三个例外时不要停等**，按 §1 的处置规则跳过并记录。
3. **上下文会被压缩。** 因此**每完成一小项立刻写台账**，不要攒着。
   台账是跨压缩、跨会话的唯一状态载体；写在对话里的结论会丢。

**建议节奏**：T1 最小版 → T2 → T3（两项小而确定，用来确认闸门仍绿）→ T4 勘查（可并行）
→ T5 → T6 → T7 按表取用。任何时刻卡住超过两次尝试，就换任务并把卡点写进台账。

## 5. 语料与法务：不要随便拉书

- **验证不需要新书**。语料内部已有见证（§4 T4/T7 实测）。
- 若确要取书：**同一著作的第二版本 > 易類新书（目录里还有 165 部未取）> 其他**。
  **術數新书暂不取**——手上 20 部無一有第二版本，加新书只是纯增不可验证面积。
- **绝对不可入库：生成文本。** 实测五个外部「周易」项目，**三个的卦辭/解读是生成的**
  （一个用伪随机种子挑卦套模板，一个是 LLM prompt 包装，一个根本没有卦表）。
  当成"周易数据"入库 = 把无出处生成文本灌进引用系统。
- **版权按层判定，不按文件判定**：`sunls2/zhouyi` 有 **36.9%（92,714 字）**属于
  傅佩榮（1950— ，在世），另有 台灣張銘仁，且仓库无 LICENSE → **不可入库**。
- 每次获取必须记 `sha256 / source_url / fetched_at / licence`。
  已有先例：三部核心书（含底本 KR1a0001）曾无 provenance，上一会话补齐并**逐字节验证与上游一致**。
