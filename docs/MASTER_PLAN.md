## 1. 项目目标

构建一套**通用书籍研究基础设施**，使 AI 对一本书的处理达到"真正读过"的程度。

"真正读过"拒绝模糊表述，由 `BOOK_AI_ARCHITECTURE.md` 的 **G1–G9** 九条可验证判据定义。
本方案不重复那张表，只强调其中两条构成硬底线：

- **G2 定位**：引用锚点必须能在原始文件里**字符串匹配**到。这一条排除了「AI 生成的页码」
  和「chunk id」两类伪引用。
- **G6 引用**：引用错误率 ≤ 1%，且必须**可执行地测量**，不能靠人工抽查的印象。

其余七条（找原文、区分版本、跨单元关联、比较注家、认输、知识分层、长期研究）是能力目标。

**当前判据达成情况见 `TASK_LEDGER.md` §1，实测命令 `python scripts/assess_goals.py`。**

## 2. 范围边界

**在范围内**：文本层可信的书（古籍纯文本、EPUB、文本层 PDF）；多版本/多译本同一著作；
带正典地址体系的作品；无正典地址的散文（退化为只有页锚点）。

**入库前必过三道判定**（新增,由外部仓库核查推动）:

1. **是文献还是生成物** —— 见下「绝对不可入库」
2. **版权分层** —— 同一文件内可能混着公版原文与在世作者注解。实测 `sunls2/zhouyi`:
   **36.9% 的文字（92,714 字）在 傅佩榮（1950— ）标题之下**,另有 台灣張銘仁,且仓库无 LICENSE。
   → 逐层判定,不按文件判定;混排文件必须先剥离再考虑
3. **白話文与經文必须分离** —— 混排比版权问题更危险:读者要原文而系统返回现代白話,
   属于伪造引文的一种

**明确不在当前范围**：
- OCR 路径（需 vision API key，本机不具备 → 检测到损坏就隔离并报告，不修复）
- 向量检索与 embedding（无 CUDA，CPU 方案未评估）
- 知识图谱（前置条件见 §7）

**绝对不可入库的一类内容：生成文本。** 这条是硬约束,不是偏好。

实测五个外部「周易」开源项目,**三个的卦辭/解读是生成的**——一个用伪随机种子挑卦再套模板
（`hexagram = pick(hexagrams, seed + numberA*8 + numberB)`,解读带 `score: baseScore`）,
一个是 LLM prompt 包装,一个根本没有卦表。它们看起来都像「周易数据」。

若把这类内容当 Source 入库,等于把**无出处的生成文本**灌进一个引用系统——与本项目修掉的
`有能乾○九乾` 伪造引文同类,只是从正门进来。因此:

- 外部数据入库前必须判定它是**文献**还是**生成物**,判据是「能否追溯到印本/底本」
- 生成物若确有用途,只能进 Derived（§6）,永不进 Source,且必须标注生成方式
- **在 G8 三类隔离落地之前,不接受任何外部生成内容**——没有隔离机制就没有安全的存放处

**测试数据不是设计边界**。《周易》与术数类是第一批语料，不是系统假设。
这一点已被实测检验过一次：schema 曾把周易的地址体系写成列名，换一部书就存不进去。

## 3. 分层架构

```
   Source Adapter   Kanripo · Gutenberg · Local        + provenance(sha256/url/time/licence)
          ↓
   Parse Layer      双引擎并行 → 分歧即质量闸门          ★偏离1
          ↓
   Normalise        異體字折叠 · 占位符 · 逐字切分        ★偏离2
          ↓
   Structure        单元切分 + 双地址 + 层(layer)        ★偏离3
          ↓
   Quality Gate     独立见证交叉校验 → 损坏/缺陷分类      ★偏离4
          ↓
   Index            SQLite FTS5（逐字切分）+ 元数据
          ↓
   Agent            检索即推理：判型→选书→读→扩展→验证
          ↓
   Output           答案 + 引用 + 证据充分性判定
```

四处偏离常规流水线，每处都由实测强制，理由见 `DECISIONS.md`：

**偏离 1 — 解析层双引擎**（D-001）。两个引擎失败方式相反：PyMuPDF 静默产出貌似合理的错字，
markitdown 显式输出 `(cid:N)`。分歧处即不可信字符，质量闸门几乎免费。

**偏离 2 — 归一化是独立可测层**（D-003）。異體字有两种独立形态：单书内混用、跨来源系统性
相反；NFKC 完全无效。折叠必须在索引与查询**两端**施加，因此必须能独立测试。

**偏离 3 — 每个单元两个地址**（D-005）。页锚点是版本局部的，能引用不能对齐；正典地址能
对齐不能指向印本位置。职能不同，必须并存。对不上就是 `unknown`，不猜。

**偏离 4 — 质量闸门用独立见证，不用表面统计**（D-012）。字符稀有度探测器在自己的已知阳性
对照上失败；跨版本同址一致性通过。**没有已知阳性对照的质量闸门等于没有闸门。**

**见证有三级,优先级从高到低**（D-017）:

| 级别 | 例子 | 为何可信 |
|---|---|---|
| **无关字形的结构见证** | `biangua/gua.json` 的六位极性串 | **纯位串,与简繁/異體完全无关**。64/64 吻合验证了我们最高风险的一次推导 |
| 同址跨版本文本见证 | KR1a0006 vs KR1a0007 | 有文本依存关系,分歧即缺陷 |
| 跨来源正字法见证 | Kanripo vs Gutenberg vs sunls2 | 只能产出折叠候选,不能判对错 |

**推论一条**:凡能化为**与字形无关的结构量**（位串、序号、计数）的东西,优先用它做见证。
本项目因为极性是纯位串,才能在**完全不处理简繁**的前提下确认卦身份映射正确;
名称差异随后就只可能是正字法或命名约定,不可能是映射错误。

## 4. 地址体系插件模型（核心设计）

这是本方案与 v0.1 架构的最大差别，由通用性证伪测试推动（D-015/D-016）。

**旧设计（已废弃）**：`unit` 表有 `gua INTEGER, gua_name TEXT, yao TEXT` 三个字面列。
后果：周易的地址体系**就是** schema，第二种体系根本无法存储。

**现设计**：地址与体系解耦。

```sql
scheme      TEXT     -- 'zhouyi' | 'bcv' | 'play' | 'stephanus' | NULL
addr_name   TEXT     -- 容器名：卦名 / 卷名 / 剧名
addr1       INTEGER  -- 序号层：卦號 / 章 / 幕      （要能排序与范围查询）
addr2       TEXT     -- 标签层：爻位 / 節 / 場
```

| scheme | addr_name | addr1 | addr2 | 状态 |
|---|---|---|---|---|
| `zhouyi` | 卦名 乾 | 卦號 1..64 | 爻位 九三 / 用九 | 已实现 |
| `bcv` | 卷名 Genesis | 章 | 節 | 已实现（KJV/WEB，35,787 单元） |
| `yilin` | 之卦名 | 本卦號 1..64 | 之卦名 | 已实现（焦氏易林，5,032 单元 = 64×64 矩阵 4,096 cells；R59b 修正单元/cells 口径） |
| `booksec` | 书名（BOOK） | 节序 | 节 | 已实现（Herodotus/Darwin/Plato 等，4,247 单元） |
| `play` | 剧名 | 幕 | 場 | 已实现（Shakespeare，6,512 单元） |
| `euclid` | 书名（BOOK） | 命题序 | 命题 | 已实现（欧几里得，649 单元） |
| `stephanus` | 篇名 | Stephanus 页 | 分节 | 未实现（实测 0 单元；Plato 现走 booksec） |
| `NULL` | — | — | — | 无正典地址，只有页锚点 |

> 单元数为 2026-08-16 对 `data/index/corpus.db` 的 `GROUP BY scheme` 实测，
> 以实测为准（本表状态曾把 play 误标"未实现"，R39b 修正）。

**`addr2` 必须是 TEXT**：周易的 `用九`/`用六` 是真实可寻址单元但**没有序号**。这比圣经的
章节号更苛刻，正好用来检验列型选择是否真的通用。

**新增一种体系必须做的事**（这是可复制的清单，见 `LESSONS.md` L-08）：
1. 写一个解析器，输出 `(addr_name, addr1, addr2, text)`
2. **用正典序列的 LIS 分段**，不要沿用最近标题
3. **只接受结构性地址标记，排除交叉引用**
4. 过滤掉目录（目录是第二条完整有序链，LIS 会把两条缝在一起）
5. 拒绝以句读结尾的候选标题（散文句会通过命名占比测试）
6. 给 3–5 个**控制用例**，其中至少一个是已知错答

`gua=` / `yao=` 作为 `scheme='zhouyi'` 上的便利别名保留，并有 `unit_zhouyi` 视图。

## 5. 数据模型

```
Work            抽象著作（"周易"、"Bible"）
 └─ Edition     具体文本（KR1a0001/tls、KR1a0031、KJV、WEB）
     └─ Unit    最小可引用单元
         ├─ page_anchor    版本局部，用于引用，必须可字符串匹配
         ├─ canonical_addr (scheme, addr_name, addr1, addr2)，跨版本，可为 NULL
         ├─ layer          經 / 傳 / 注 / 疏 / 圖 / 十翼 / 正文
         └─ attribution    注家 / 译者 / 编者
Agent 侧（已实现，2026-08-16 R22b-R36b）：
Concept · Entity · Claim · Interpretation · Evidence
实现载体：`src/guji/mcp_server.py`（MCP stdio server，12 工具：search/addr/
compare/concept/research_tool/threads/bookstudy_structure/bookstudy_chapter/
compare_works_tool/book_summary_tool/add_local_work_tool/record_claim_tool）
+ 协议级自测 `python -m guji.mcp_server --selftest`；Agent 可检索、读整书、
两书对照、做 Book Summary、加本地书、并把结论写入 G9 线程
（record_claim_tool，G8 纪律——断言必须带真实证据）。web 侧同源能力见
`web/app.py` 与 `web/static/index.html`（古籍读书面板 9 个研究 tab）。
```

**Work 与 Edition 必须分开**：实测证明"同一部书"不是单一文本——原本/別本周易本義 是同著作
两版；Kanripo 与 Gutenberg 的《易经》体量差 1.72 倍且用字约定相反。合并会静默抹除这些差异。

**`layer` 必须逐单元判定，不能按书赋值**。曾经每部书只有一个 layer，导致被引的 `經` 与注家
自己的 `注` 同标为 `注`，合并时还被融成一块打乱次序。

**`Claim` 与 `Interpretation` 必须区分**：前者是原文说了什么（可引用），后者是注家或 AI 的
解读（需标注主体）。混同会让"比较注家"失去意义。

**`unknown` 是一等公民**。宁可标注不知道，也不要写入错误归属。更进一步：版本自己把地址刻错
时，应报告为**源文异常**，而不是记 unknown——那是一个关于该版本的可核验发现（D-014）。

## 6. 三类知识物理隔离（G8，已实现）

```
Source Knowledge      来自原文，必须有可匹配的 page_anchor，不可修改
Derived Knowledge     AI 推导，必须记录推导链与所用 Evidence
Conversation Memory   用户与 AI 的讨论过程
```

**实现状态（2026-08-16 核实，早期版本此处曾写"未实现/空真"，已过时）**：
Source 在 corpus.db（随构建重建）；Derived/Conversation 在 knowledge.db
（`knowledge_schema.sql`，**不可重建**——这正是必须两个文件的原因）。
`src/guji/knowledge.py` 是窄 API，把规则做成调用者绕不过去的约束：
`record` 拒绝无证据断言（refusal 是唯一例外，G7）；evidence 只能从检索 Hit
构造（自动携带 file+anchor+地址，无法附着非真实段落）；`verify` 重读
data/raw 复核每条 quote，证据不再匹配的断言标 STALE 拒绝服务。
实测：assess_goals G8 = PASS；跨会话研究线程见 `scripts/research_thread.py`（G9）。

## 7. 实施顺序（按当前风险重排）

顺序由风险决定，不由模块依赖决定。**带 ⚠ 的是"越晚做越贵"的结构性项。**

1. ~~解决卦/爻对齐~~ 已完成（D-006，97.4%）
2. ~~異體字折叠表~~ 已完成（D-003/D-013，48 对，含否决清单）
3. ~~ingest + FTS5 检索骨架~~ 已完成（D-008/D-010）
4. ~~补非古籍测试书验证通用性~~ 已完成并**证伪了原设计**（D-015/D-016）
5. ⚠ **G1 评测集**。没有它，"能找到原文"永远不可测，后续 Agent 工作**没有验收标准**
6. ⚠ **G8 三类知识分层**。schema 改动，越晚越贵
7. 引用披露：层过滤引文需标记（53% 的单元是子序列而非连续引文）
8. 质量闸门产品化：损坏区在索引中标记，检索结果给出警告
9. Agent 多跳与证据集（G4）、认输机制（G7）
10. 跨会话研究线程（G9）
11. MCP / Skill —— 仅在成熟方案不够用时才自建

**在第 5 步之前不建知识图谱。** 否则会把未经验收的归属固化进实体关系，后期无法清除。
建图前另须确认 `differs` 类異文不会被实体抽取抹平。

## 8. 每阶段完成判据

一个阶段"完成"必须同时满足三条，缺一不可：

1. **有可执行的复验命令**，写入 `TASK_LEDGER.md`
2. **有已知阳性对照**，且对照失效时脚本 exit 非零
3. **断言的是返回内容，不是计数**。计数型断言在 FTS5 隐式 AND 下会假通过，
   短语相邻性缺陷正是这样漏掉的（D-010）

新增：任何"单元数/覆盖率变化"必须附**守恒检查**。单元数本身分辨不出「合并」与「丢数据」。
守恒检查用**有序子序列**，不用多重集——多重集测不出重排，而重排正是本项目修掉过的缺陷。

## 9. 已否决组件（不要重新评估，除非前提变了）

| 组件 | 结论 | 前提 |
|---|---|---|
| Docker | 不采用 | 本机无 Docker |

| 退化段落重试选位 | **实测否决** | 换一类错误且分数下降，详见 §4 |
