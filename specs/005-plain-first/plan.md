## 2. 古籍区形态：L2 单层总折叠（L1 按书平铺已被实测推翻）

三种层级形态 × 三个用例实测（都叠加顺序反转 + 提交后滚动）：

| 形态 | 7 书 | 8 书 | **6 书** | 判据 2 |
|---|---|---|---|---|
| L1 按书组头直接平铺（初版 V6） | 2,991px +257 | 3,187px +61 | **3,288px −40 = 5 屏** | ❌ |
| **L2 一个总折叠 → 内含按书分组** | **2,607 +641** | **2,739 +509** | **2,968 +280** | ✅ |
| L3 一个总折叠 → 内含 12 条平铺 | 2,607 +641 | 2,739 +509 | 2,968 +280 | ✅ |

**L1 被推翻的原因值得记下**：它的高度不随书数单调——6 书用例反而最高。
组头文本在 375px 下**换行**（`《穷通宝鉴》 3 段` 一行，长书名两行），
实测 492/8 = 61px 而非设计的 44px；且 6 书那一案的白话段本身更长。
初版「书数越多越高、最坏 8 书余 288px」的推断**是错的**——我当时只测了
7 书与 8 书，没测 6 书，把单调性当成了理所当然。这正是 D-150a 说的
「判据不能建立在会漂移的量上」，我自己也踩了一次。

**选定 L2**（而非等效的 L3）：默认只有一个 44px 的总入口，高度**与书数、
段数完全无关**——五案古籍区实测恒为 44px。L3 数值相同但少一级书目导航；
L2 展开后按书分组，用户能看清「12 段来自 7 部书」，与 003/004 的信息层级一致。

形态（三级，每级默认折叠）：

```
📜 古籍原文依据 · 12 段 / 7 部书 ▾        ← 唯一默认可见项，44px
  └ 《穷通宝鉴》 3 段 ▾
      └ 穷通宝鉴 @? (qiongtongbaojian_001.txt) · 因「月柱」被选中 · 4,123 字 ▾
          └ [原文全文，逐字节等于 API]
```

## 3. 折叠机制仍选 `hidden`——但理由与初版不同

R129a 的 `isHidden` 已识别关闭态 `<details>`，所以两种机制探针都认。
实测对照（CASE7/CASE8，都叠加 L1 分组）：

| 机制 | 探针「定位到 / 判为已折叠」 | 判据 4 | 判据 8 逐字节 |
|---|---|---|---|
| `<details>` | **0 段 / 0 段** | 0%（**空过**） | True |
| `hidden` + 按钮 | **12 段 / 12 段** | 0%（正面确认） | True |

`<details>` 关闭态的 `innerText` 为空字符串，探针的古籍定位器
（`norm(e.innerText).includes(head)`）**一段都命中不了** → 判据 4 拿到 0%
是因为「找不到任何古籍」，而不是「找到了且已折叠」。这种通过方式无法区分
「折叠成功」与「原文被删了」——**恰恰是宪法第三条最该防的情形**。

`hidden` 下探针报「定位到 12 段、其中默认已折叠 12 段」，是正面证据。
**同一判据下，`hidden` 的通过是可核验的，`<details>` 的通过是空的。**
故选 `hidden` + `<button aria-expanded>`（键盘可达由 button 原生保证）。

不再需要 `[hidden]{display:none!important}`：被 `hidden` 的都是我新建的
普通 `div`，实测 `getComputedStyle(cb-0).display === 'none'` 直接成立（§1 表）。

`web/static/index.html` **不改**（不再需要藏首页块，无需补容器）。

### 4.2 去重（判据 5，清偿 R128a-01）

`buildBaziResult`（`app.js:608-611`）渲染 `j.evidence` 全文，
`renderWarm`（`:301-309`）又渲染 `warm.citations`。实测同源：
12/12 条目对应、`citation` 字符串逐条相等、
`citations[i].text === evidence[i].text[:220]`；页面 `.ev-item` = 24 个而 API 12 段。

**处置：warm 模式只渲染一处，数据源用 `j.evidence`（全文版）。**
判据 8 要求展开原文与 API 逐字节一致，而 `warm.citations` 是
`interpreter.py:308` 的 220 字截断版，展开它不可能逐字节一致。
`renderWarm` 不再渲染 citations；专业模式路径**一字不改**（判据 9）。

### 4.3 折叠件契约（判据 3/4/5/6/7/8）

```html
<div class="cite-wrap">
  <div class="cite-top">
    <button type="button" class="cite-toggle" aria-expanded="false"
            aria-controls="cite-all">📜 古籍原文依据 · 12 段 / 7 部书 ▾</button>
    <div class="cite-top-body" id="cite-all" hidden>
      <div class="cite-group">
        <button type="button" class="cite-toggle" aria-expanded="false"
                aria-controls="cg-0">《穷通宝鉴》 3 段 ▾</button>
        <div class="cite-group-body" id="cg-0" hidden>
          <div class="cite-item">
            <button type="button" class="cite-toggle" aria-expanded="false"
                    aria-controls="cb-0">
              穷通宝鉴 @? (qiongtongbaojian_001.txt) · 因「月柱」被选中 · 4,123 字 ▾
            </button>
            <div class="cite-body" id="cb-0" hidden>…原文全文…</div>
          </div>
        </div>
      </div>
    </div>
  </div>
</div>
```

- **默认可见只有总入口一行**（44px），判据 3 实测最长可见块 71–93 字
  （来自白话段，不是古籍）。
- **出处**（判据 5/7）：`citation` 在第三级按钮上（实测形如
  `穷通宝鉴 @? (qiongtongbaojian_001.txt)` 或
  `星命溯源 @KR3g0035_WYG_004-10b (KR3g0035_004.txt)`），与原文同级展开。
  判据 5 的解释：折叠态两者都不算「显示原文」（不可见但可取），展开态同屏。
  绝不出现「有原文没出处」或「有出处取不到原文」——与 R118a-03 判定方向一致
  （那条 MAJOR 反对的是**出处丢失**，不是反对折叠）。
- **逐字节一致**（判据 8）：`.cite-body` 用 `esc(h.text)` 原样输出，不 trim、
  不改标点、不合并空白、不 `[:220]`；CSS 加 `white-space:pre-wrap` 保留换行。
  实测 `cite-body.textContent === evidence[0].text` → True（五案）。
- **可核验性**（判据 6/7）：`hidden` 不影响 `textContent`，
  探针实测「定位 12 段 / 折叠 12 段」+ `textContent` 22,965 字。
- **点击区与对比度**（005 判据 16 / 003 判据 1-3）：`.cite-toggle`
  用 `min-height:var(--tap)`（`styles.css:573` 已有先例），无动画（判据 18）。
- **`why` 上屏**：12/12 条 `why` 非空（「月柱」「日柱」「年柱」），
  第三级摘要行显示「因『月柱』被选中」。只展示已有字段，不改检索。

### 4.4 顺序反转 + 提交后滚动定位

**顺序反转（仅 warm 分支）**：`buildBaziResult` 改为

```
h2 → 收藏 → pill-row(四柱) → nayin
  → renderVoice(j)        ← warm：切换器 / L0 / reply / 能量卡 / badge / 6 段白话
  → 古籍总折叠（44px）
  → (pro 模式) renderCalc
```

⚠ **pro 分支顺序保持现状**——判据 9 与 `pro_render_baseline.json` 的 `h3` 顺序
（`ten_gods / five_elements / relations / day_luck / 📜 古籍依据 / 📖 解读`）钉死了它。

**判据 1 的定位（替代初版 `focusResult`）**：提交成功后把结果区顶部滚到视口顶部
（`window.scrollTo({top: resultTop - 8, behavior:'auto'})`）。实测对比：

| 定位方式 | L0 相对视口 y | 判据 1 |
|---|---|---|
| 什么都不做（仅折叠+反转） | 587–793px | ✅ 但取决于表单高度 |
| **显式滚到结果区顶部** | **353px** | ✅ 确定 |
| 滚到一句话本身 | 60px | ✅（过度，四柱被推出屏） |

「什么都不做」也能过，但那是**偶然**——它取决于点击 `#submit` 时的滚动位置
与表单高度，表单加一行就可能超。选显式滚动：确定行为，且 `.brand` /
`#dailyCard` / `#funcGrid` **一个都不隐藏**，spec 那条「不得把今日入口永久藏死」
天然满足（它们仍在文档里，向上滚即见）。

`behavior:'auto'` 而非 `smooth`：reduced-motion 下不产生动画（判据 18），
也避免探针在滚动未完成时取到中间值。
