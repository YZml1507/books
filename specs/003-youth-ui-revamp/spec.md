## 本文件的两条硬门槛（写之前先声明，不满足就不许写进来）

宪法第六条要求 spec **只写 WHAT 和 WHY，不写 HOW**——不涉及技术栈、API 形状、
代码结构，写给非技术干系人看。因此下文不出现任何文件名、函数名、CSS 属性。

在此之上，本项目额外要求每条要求满足**其一**：

**(a) 可自动测量。** 有当前值、有目标值、有一条能跑出这两个值的命令。
**(b) 可回滚。** 视觉方案能一键切回旧样式。

第 (b) 条是「审查轨自主决定审美方向」这件事得以成立的前提：方向选错了，
用户一键切回即可，不构成损失。没有回滚能力的审美改动，就不是可自主决策的改动。

**基线来源**：下文所有「当前」数字都出自同一条命令，非估计、非印象：

```powershell
cd C:\Users\Lenovo\Desktop\projects\books-audit
C:\Users\Lenovo\Desktop\projects\books\.venv\Scripts\python.exe probes\probe_ui_baseline.py
# 完整数据 logs/ui_baseline.json；三个视口截图 logs/baseline_*.png
```

实测时间 2026-08-20。该 probe 是**量尺不是闸门**——它不做通过/失败判定，
只产出可比对的当前值。验收时重跑同一条命令比对目标值即可。

## 为什么现在做这件事（WHY）

REPAIR 阶段解决的是「能用」。实测结论是它现在真的能用了：35 个真浏览器用例
全通过、191 个字段读取点零漂移。但「能用」和「想用」之间还有一段距离，
而这段距离**大部分不是审美问题，是可测量的缺陷**：

- **59 个可点击元素小于 44×44 像素**（375px 视口实测）。手指点不准要重试，
  这是「廉价感」最直接的来源之一，也是 WCAG 2.5.5 的明确要求。
- **31 处文字对比度低于 WCAG AA**（最低 3.18:1，要求 4.5:1）。看着费劲，
  且对视力弱的用户是可达性障碍。
- **293KB 动画资源完全没接线**，而已接线的全部前端资源合计只有 103KB。
  仓库里躺着近三倍于全部前端代码的动画能力没用上。

把这三项讲清楚很重要：**精致感往往就是这些客观量的总和**。
「不够高级」通常不是配色不够花，而是对比度不足、点击区过小、动画掉帧。
本 spec 因此把绝大多数「体验」要求转写成了可测量的代理指标。

同时必须说明**当前已经达标、不要动坏它的项**：

| 项 | 当前实测 | 要求 |
|---|---|---|
| 375px 视口横向滚动 | **0px** 溢出 | 保持 0 |
| 长任务（>50ms） | **0 个**（三个视口均是） | 保持 0 |
| `prefers-reduced-motion` | 已生效（动画 2 → **0**） | 保持生效 |
| 首屏内容绘制 | 375px **128ms** / 1280px 516ms | 不得变慢 |
| 首屏 console 错误 | **0** | 保持 0 |

这张表是「改进不得引入回归」的基线。任何一项变差都算 MAJOR。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 手指点得准（Priority: P1）

**作为**用手机单手使用的年轻用户，**我想要**每个能点的东西都足够大、
点了就中，**以便**不需要眯眼瞄准或反复重试。

**Why this priority**: 这是所有「廉价感」里最容易被感知、也最容易被测量的一项。
59 个过小目标里包含日期输入、性别选择、标签切换——即核心流程的必经之路。
它同时是可达性要求（WCAG 2.5.5 Target Size），不是纯偏好。

**Independent Test**: 在 375px 视口下枚举全部可点击元素的实际渲染尺寸，
统计小于 44×44 的个数。

**Acceptance Scenarios**:

1. **Given** 375px 视口首页，**When** 枚举全部可点击元素，
   **Then** 小于 44×44 的个数为 **0**（当前 59）。
2. **Given** 1280px 视口，**Then** 同一指标为 **0**（当前 56）。
3. **Given** 任意视口，**Then** 相邻可点击元素之间有足够间隔，
   不存在两个目标边界重合导致误触的情形。
4. **Given** 放大到 200% 页面缩放，**Then** 仍无横向滚动、
   所有目标仍不小于 44×44。

---

### User Story 2 — 字看得清（Priority: P1）

**作为**在地铁上、在阳光下、或视力一般的用户，**我想要**所有文字都足够清晰，
**以便**不用凑近屏幕才能读运势结论和古籍原文。

**Why this priority**: 31 处低于 AA，其中包含每日运势的「宜/忌」结论
（实测 3.18:1）——那是用户最想看的一句话，却是对比度最差的一处。
古籍原文更需要长时间阅读，对比度不足直接影响可读性。

**Independent Test**: 计算页面上每个含文字元素的前景/背景对比度，
与 WCAG AA 阈值（正文 4.5:1、大字 3:1）比对，统计未达标个数。

**Acceptance Scenarios**:

1. **Given** 任意视口首页，**When** 计算全部文字元素对比度，
   **Then** 低于 AA 的个数为 **0**（当前 31）。
2. **Given** 展开任一功能的结果区（排盘、检索、六爻等），
   **Then** 结果区内文字同样 0 处低于 AA。
3. **Given** 古籍原文引文区，**Then** 正文对比度不低于 AA，
   且出处标注仍然可读（出处不得为了"低调"而降到 AA 以下）。
4. **Given** 深色与浅色两套主题（见 User Story 5），**Then** 两套各自都 0 处低于 AA。

---

### User Story 3 — 有质感的动效，且可以完全关掉（Priority: P2）

**作为**喜欢精致交互的年轻用户，**我想要**点击、切换、出结果时有恰当的动效反馈，
**以便**感觉这个产品是"活"的而不是一张静态表单。
**同时作为**对动画敏感（前庭功能敏感、易眩晕）的用户，**我想要**能完全关掉它们。

**Why this priority**: 仓库里已有 293KB 动画资源未接线，而全部已接线前端资源
只有 103KB。这是**现成素材**，用它不引入任何新的外部依赖。
但动效是双刃的：掉帧的动画比没有动画更廉价，因此下面每条都带性能上限。

**Independent Test**: 在动效播放期间采集长任务；在
`prefers-reduced-motion: reduce` 下统计仍在运行的动画数。

**Acceptance Scenarios**:

1. **Given** 任意交互触发动效，**When** 动效播放期间采集长任务，
   **Then** 超过 50ms 的长任务数为 **0**（当前 0，**不得退步**）。
2. **Given** 系统设置为「减少动态效果」，**Then** 运行中的动画数为 **0**
   （当前已达标：2 → 0，**不得退步**）。
3. **Given** 首屏加载，**Then** 首次内容绘制不慢于当前值
   （375px **128ms** / 1280px **516ms**）。
4. **Given** 结果区渲染大量内容（排盘结果实测 31893 字符），
   **Then** 滚动过程无可感知掉帧，长任务仍为 0。
5. **Given** 动效已接线，**Then** 已接线静态资源总量的增长在可接受范围内，
   并在 `plan.md` 中给出明确上限与实测值（当前 103KB）。

---

### User Story 4 — 首屏更快、更轻（Priority: P2）

**作为**用移动网络打开页面的用户，**我想要**页面尽快出现内容，
**以便**不面对空白屏等待。

**Why this priority**: 当前首屏已不慢（375px 实测 FCP 128ms），
所以这条的重点**不是继续压缩，而是在加动效与主题之后不许变慢**。
把它写成要求，是为了防止「为了好看牺牲速度」这种常见退化。

**Independent Test**: 采集 DOMContentLoaded、load、首次内容绘制，
以及三个主要接口的响应延迟（多次采样取 p95）。

**Acceptance Scenarios**:

1. **Given** 首屏加载，**Then** 首次内容绘制不慢于基线（见 User Story 3.3）。
2. **Given** 主要接口，**Then** p95 延迟不高于基线：
   健康检查 **18.9ms**、书目 **79.7ms**、检索 **17.2ms**、排盘 **132.1ms**。
3. **Given** 首屏，**Then** 重复访问能命中缓存（首次与二次访问的传输量有可测差异）。
4. **Given** 首屏，**Then** 不因视觉升级引入额外的阻塞式请求。

---

### User Story 5 — 审美方向可一键回滚（Priority: P1）

**作为**这个产品的所有者，**我想要**新的视觉方向能一键切回旧样式，
**以便**即使我不认可审查轨自主选定的审美方向，也不损失任何已完成的工作。

**Why this priority**: **这条是本 spec 里唯一一条「机制」要求，也是最重要的一条。**
审查轨对审美有最终决定权、且不询问即执行——这个安排能成立的**唯一前提**
就是选错了可以零成本撤回。没有这条，其余所有审美要求都变成不可逆的赌注。

**Independent Test**: 在同一次会话内来回切换新旧两套视觉，
每次切换后页面功能与内容完全不变。

**Acceptance Scenarios**:

1. **Given** 新视觉已上线，**When** 切换到旧样式，
   **Then** 页面回到 REPAIR 阶段结束时的视觉，且**全部功能照常可用**。
2. **Given** 任一套视觉，**Then** 35 个真浏览器用例全部通过——
   **切换视觉不得破坏任何功能**。
3. **Given** 任一套视觉，**Then** 对比度、点击目标、横向滚动、长任务
   四项指标各自达标（新样式按新目标，旧样式按其原有水平）。
4. **Given** 切换动作，**Then** 用户的已有数据（历史、收藏、偏好）不受影响。
5. **Given** 两套视觉，**Then** 用户的选择在下次打开时保持。

---

### User Story 6 — 内容层次一眼可辨（Priority: P3）

**作为**同时用它读书和算命的用户，**我想要**一眼分清「古籍原文」「运算事实」
「系统转述」三类内容，**以便**知道哪句话有出处、哪句话是推算。

**Why this priority**: 这是本项目的**立身之本**在视觉层的投影。宪法第三条要求
引用与生成分离；REPAIR 阶段刚修掉一条「古籍依据出处永久为空」的缺陷
（R118a-03）——出处在视觉上必须无法被忽略，否则同类问题会以「看不见」的形式
复发。这是审美要求里唯一一条直接源自宪法的。

**Independent Test**: 检查三类内容是否有稳定且可区分的视觉标识；
检查每条古籍引文是否都带非空出处。

**Acceptance Scenarios**:

1. **Given** 任一含引文的结果区，**Then** 每条引文都有非空出处标注
   （当前已达标，**不得退步**）。
2. **Given** 排盘结果，**Then** 古籍原文、运算坐标、系统转述三类在视觉上可区分，
   且区分方式在全站一致。
3. **Given** 系统转述文字，**Then** 明确标示它不是古籍原文、也不是现实决策依据。
4. **Given** 任一结果区，**Then** 页面任何位置不出现内部技术字段名
   （如 `ten_gods`、`five_elements` 这类原样键名，当前排盘结果区仍有）。

## Assumptions

- 动效使用仓库内既有素材，**不引入新的外部依赖、不联网抓取新资源**
  （宪法第二条红线第 3 项）。若某方向必须引入新依赖，
  按处置规则记为 BLOCKED 并换方案，不询问。
- 本阶段不改变任何算命/读书的**计算结果**。视觉层不得影响坐标事实与引文。
- 「年轻化」的具体方向（配色、版式、动效性格）由审查轨自主决定，
  候选与否决理由记入 `docs/DECISIONS.md`；用户的否决权由第 12 条判据保障。
- 移动端以 375px 宽为基准视口（当前实测已无横向滚动，是可守住的基线）。

## Out of Scope

- 新增算命品类或新的语料入库（属功能扩展，另立 spec）。
- 重新引入生成式模型解读——REPAIR 阶段刚移除，且本阶段核心决策之一
  就是砍掉它省成本。
- 原生 App 或桌面打包形态的改动。
- 对 `data/` 下语料与清单的任何修改。
